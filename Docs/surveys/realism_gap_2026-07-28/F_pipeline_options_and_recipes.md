# F — 파이프라인 선택지와 콘텐츠별 사실성 레시피 (2026-07-28)

조사 범위: (1) Isaac Sim 자체 절차생성을 유지할 것인가 / 외부 스택(Infinigen·Blender·UE5)으로
갈아탈 것인가, (2) 갈아타든 아니든 렌더를 "장난감"에서 벗어나게 하는 콘텐츠별 구체 레시피.

표기 규약: **[확인]** = 1차 출처를 직접 열람해 검증 / **[측정]** = 본 조사에서 우리 코드·이미지를
직접 계측 / **[추정]** = 조사자 추론(검증 필요).

## §1 결론 — 스택은 갈아타지 않는다. Isaac Sim 유지 + Blender를 "에셋 공장"으로 병설한다

### 1.1 권고안 한 줄

> **Isaac Sim(USD/Python 절차조립 + RTX PT)을 씬 그래프의 주 무대로 유지하고,
> Blender 4.5는 "오프라인 에셋 베이커리"로만 붙인다.**
> 즉 **하이브리드이되, 무게중심은 지금 그대로 둔다.** 33씬 스크립트는 한 줄도 버리지 않는다.

### 1.2 이 결론의 결정적 근거 — 우리는 이미 증거를 갖고 있다

가장 중요한 발견은 외부 조사가 아니라 **우리 저장소 안**에 있었다.

**[측정] `assets/NegObsGround.mdl` (438줄) — 정교한 커스텀 MDL이 이미 존재하고, 33개 본편/배치 씬 중
어느 것도 이것을 쓰지 않는다.** 참조하는 파일은 오직 `Practice_TerrainGen/negobs_look_check_v1.py`
(휴면 중인 별도 룩데브 프로젝트) 하나뿐이다.

이 MDL이 이미 구현하고 있는 것:

| 기능 | 구현 내용 | 해결하는 결함 |
|---|---|---|
| 노멀 가중 소프트 트라이플래너 | 3면 투영 블렌딩 | OmniPBR `project_uvw` 하드 축전환 → 경사면 텍스처 늘어남 |
| 정점 primvar 크로스페이드 | `scene::data_lookup_float("blend_tw"/"blend_wb")` | 재질 경계 삼각형 톱니 → **픽셀 단위 전이대** |
| 반복 파괴 (3중) | ① 파장 10~20 m 저주파 albedo 명도·채도 변조 ② 90° 회전 패치 혼합(월드 노이즈 마스크) ③ 밝은 스페클 채도 억제 | 단일 타일 반복 노출 |
| roughness 공간 노이즈 | 파장 1.2 m 변조 | 광택이 균질 띠로 보이는 문제 |
| 경계 프랙탈화 | `blend_edge_noise` (w(1-w) 가중) | 경계선이 수학적 직선인 문제 |

그리고 이 MDL을 실제로 쓴 렌더(`Practice_TerrainGen/look_check/auto/deep_r2/pt_noon_overview.png`)는
**같은 Isaac Sim, 같은 RTX PT, 같은 PolyHaven HDRI**로 렌더됐는데도 scene04·scene17과 질적으로
다른 층위에 있다 — 타일 반복이 보이지 않고, 재질 전이가 부드럽고, 미세 기복이 살아 있다.
해당 룩데브는 **4.08/5 합격** 판정을 받았다(메모리 기록).

> **따라서 판정: 렌더러는 병목이 아니다. 병목은 Isaac Sim 안에서의 우리 저작(authoring) 방식이다.**
> 스택을 갈아타면 이 격차가 저절로 메워질 것이라는 기대는 오진이다. 4.08/5를 받은 룩데브 성과가
> 프로덕션 씬 라이브러리로 **back-port 되지 않은 기술이전 실패**가 문제의 큰 몫이다.

### 1.3 두 번째 결정적 근거 — 결함의 71%는 "텍스처를 아예 안 붙인 것"이다

**[측정]** 33씬 전체의 재질 정의(`PBR()`/`make_pbr()`) 855건을 파싱한 결과:

| 구분 | 건수 | 비율 |
|---|---|---|
| 텍스처 바인딩(`tex_path` 사용) | 245 | 28.7% |
| **상수색만 (`diffuse_color=`, 텍스처 0장)** | **610** | **71.3%** |

감독 진단의 `flat%`(국소표준편차<1/255인 "죽은 픽셀") 19.1% 평균, scene17 56.2%는
**미스터리가 아니라 이 71.3%의 직접 귀결**이다. 콘크리트·아스팔트·금속·페인트 대면적이
문자 그대로 단색 상수로 칠해져 있다.

이것은 파이프라인 문제가 **전혀** 아니다. UE5로 갈아타도 상수색을 칠하면 똑같이 평평하다.

### 1.4 갈아타지 않는 이유 (반대 근거의 기각)

| 대안 | 기각 사유 |
|---|---|
| **Infinigen 전면 채택** | **[확인] 생성 범위가 자연물 한정** — 논문 초록이 명시하는 대상은 "plants, animals, terrains, and natural phenomena such as fire, cloud, rain, and snow"이며 건물·계단·난간·교량·도로 등 인공 구조물은 없다. 우리 33씬은 **계단·난간·육교·지하도·제방·주차램프** = 전부 인공 구조물이다. 커버리지가 근본적으로 어긋난다. 게다가 **[확인] 1080p 이미지 페어당 평균 3.5시간**(그중 GPU 1시간) — 데이터셋 규모로는 불가. |
| **Blender 전면 이주(렌더까지)** | 33씬 44,000줄 USD 조립 코드를 bpy로 재작성해야 한다. 얻는 것(Cycles)과 잃는 것(RTX PT는 이미 충분히 좋다 — §1.2 증거)이 안 맞는다. 로보틱스 연동·GT 파이프라인도 전부 새로 짜야 한다. |
| **UE5 이주** | 에셋 생태계는 최고지만 **[확인] Megascans 전면 무료는 2024년 말 종료**되어 Fab 유료 전환됐고, 절차생성을 Blueprint/PCG로 재작성해야 하며, GT·로보틱스 연동을 새로 구축해야 한다. 우리 태스크에서 UE5가 주는 고유 이점(Nanite/Lumen)은 **정지 이미지 데이터셋 생성**에는 거의 무의미하다(실시간 성능 최적화 기술이므로). |
| **Unity HDRP** | **[확인] ROS-TCP-Connector가 deprecated** 되고 Simulation-ROS-Integrations로 이행 중 — 전환기 리스크. 에셋·절차생성 어느 쪽에서도 UE5·Isaac 대비 우위 없음. |

### 1.5 그럼에도 Blender를 붙이는 이유 (하이브리드의 정확한 경계선)

Isaac Sim이 **못 하는 것이 정확히 하나** 있다: **유기적 메시 저작**. USD 프리미티브
(Cube/Cylinder/Sphere) 조립으로는 나뭇잎·풀날·챔퍼진 계단코·용접 비드를 만들 수 없다.

그래서 역할을 이렇게 자른다:

```
[Blender 4.5]  ──(1회성, 오프라인)──>  [.usd 에셋 라이브러리]  ──(참조)──>  [Isaac Sim 씬 조립]
 나무/풀/난간 디테일                     assets/kit/*.usd            기존 33개 스크립트 그대로
 Geometry Nodes                          (메시+텍스처)                sc.add_ref() 한 줄 추가
 베벨·잎카드·아틀라스
```

**핵심: Blender 산출물은 "씬"이 아니라 "부품(kit)"이다.** 씬 레이아웃·카메라·조명·GT는
Isaac Sim에 남는다. 따라서 33씬 스크립트의 기하 사양(계단 치수·낙차량·카메라 프리셋)은
**100% 재활용**되고, `scene_common.py`의 `build_tree()` 같은 함수만 내부 구현이 교체된다.

**[확인] 기술적 실현성**: Isaac Sim은 ASSIMP 기반 Asset Converter로 OBJ/FBX/STL/glTF를
USD로 임포트하며, `convert_mesh.py` 유틸이 instanceable USD로 변환한다. USD 레퍼런스로
`.usd` 부품을 씬에 붙이는 것은 표준 워크플로다.

### 1.6 비용·기간·리스크

| 항목 | 값 |
|---|---|
| 금전 비용 | **0원** (CC0/무료 경로만으로 성립. 상용 구매는 선택적 가속) |
| 1주차 효과 | flat% 19.1% → **8% 이하** 도달 가능 [추정] (§11 T1 작업만으로) |
| 1개월차 | scene04류 식생 교체 완료, sat 0.30 → 0.20 |
| 3개월차 | 33씬 전체 v8 재렌더 + GT 파이프라인 착수 가능 |
| 최대 리스크 | **씬 스크립트 대량 수정에 따른 회귀** — v5 판정 21/21 합격 상태를 깨뜨릴 수 있음. 완화: `scene_common.py` 레벨에서만 고치고 씬별 파일은 건드리지 않는 변경을 우선한다(§10 A등급 작업은 전부 이 성질을 만족). |
| 기각한 리스크 | 스택 이주에 따른 2~3개월 공백 — 채택하지 않으므로 발생 안 함 |

3. **잔여 가치**: 지형(terrain) 하이트필드와 바위(rock) 에셋은 익스포트 가능성이 있다 [추정].

4. **설치 비용 대비 회수 불가** — 3.5 h/이미지 파이프라인을 세팅해서 얻는 게 "바위 몇 개"라면 손해.

> **최종: Infinigen은 도입하지 않는다.** 단 §3에서 언급하듯 Infinigen의 **나뭇잎 카드 배치 알고리즘·
> 수형 파라미터화 논리**는 논문·코드가 BSD-3이므로 **읽고 참고**하는 것은 자유이며 권장한다.

### 2.3 Blender 전면 파이프라인 상세

**[확인] Blender → USD → Isaac Sim의 실제 마찰점** (이게 "부품만 넘긴다"는 설계의 근거)

| 마찰점 | 내용 |
|---|---|
| 재질 | Blender USD 익스포터는 **UsdPreviewSurface**만 낸다. Omniverse의 MDL/OmniPBR로는 자동 변환되지 않아 Isaac 쪽에서 재구성 필요. 절차 재질(노드)은 **텍스처 베이크 필수** |
| 노멀맵 버그 | **[확인] Blender #102911** — USD 익스포트 시 노멀 텍스처를 0–1 범위로 내보내 UsdPreviewSurface 스펙(−1–1) 위반 → 다른 DCC에서 노멀이 뒤틀림. 회피 필요 |
| 인스턴싱 | Geometry Nodes 인스턴스는 **부분 지원** — Object Info / Collection Info 노드 기반 단순 산포는 `UsdGeomPointInstancer`로 나감. GN 내부 생성 지오메트리 인스턴스는 미지원 → `Realize Instances` 필요(메모리 폭증) |
| 텍스처 경로 | 절대경로로 새어나가 머신 간 이동 시 텍스처 유실 사례 보고됨 (Infinigen 이슈 #322에서도 동일 증상) |

→ 이 마찰들은 **씬 전체를 넘길 때** 치명적이지만, **부품 1개(나무 1그루)를 넘길 때**는
   전부 감당 가능하다(수동 1회 처리). **이것이 하이브리드 경계선을 "부품"에 그은 이유다.**

### 2.4 게임엔진 경로 상세

| 항목 | UE5 | Unity |
|---|---|---|
| 로보틱스 연동 | **[확인]** CARLA가 UE 5.5에서 동작, LiDAR/radar/카메라/semantic seg/ROS2 네이티브. rclUE·ROSIntegration·UE ROS2 센서 플러그인 존재 | **[확인]** ROS-TCP-Connector **deprecated**(2023 말 공지) → Simulation-ROS-Integrations로 이행 |

### 2.6 §3~§9의 공통 프레임 — "CG가 가짜로 보이는" 7가지 이유

콘텐츠별 레시피에 들어가기 전에, 모든 항목에 반복해서 등장하는 원인을 정리한다.
우리 렌더는 **7개 중 7개**에 해당한다.

| # | 원인 | 왜 뇌가 즉시 알아채는가 | 우리 상태 |
|---|---|---|---|
| 1 | **샤프 에지 (베벨 0)** | 현실에 완벽한 90° 모서리는 없다. 모든 모서리는 0.5~2 mm 둥글고 그 곡면이 **하이라이트 한 줄**을 그린다. 이 선이 없으면 즉시 CG | **전 씬 베벨 0건** |
| 2 | **엔트로피 0 (모든 것이 새것)** | 현실의 시각적 복잡성 대부분은 **시간의 흔적**(마모·오염·파손·보수)에서 온다 | 웨더링 0 |
| 3 | **완벽한 정렬·반복** | 등간격·정렬·동일 크기는 자연에 없다. 헤지 블롭 피치, 창 배열, 타일 격자 | 위상 지터 거의 없음 |

| 5 | **접지 실패** | 물체와 바닥이 만나는 선의 AO·먼지·그라우트가 없으면 물체가 **떠 보인다** | 난간·볼라드 전부 해당 |
| 6 | **텍셀 밀도 불일치 / 매크로 변주 0** | 물체마다 텍스처 해상도가 다르거나, 한 텍스처가 균일 반복되면 들킨다. **[확인] 업계 기준 배경 512 px/m, 히어로 1024 px/m** | 상수색 71.3%, 매크로 변주 0 |
| 7 | **렌즈/센서 부재 (너무 깨끗함)** | 실사에는 비네팅·수차·노이즈·DoF·톤매핑이 항상 있다. 순수 핀홀 렌더는 **비현실적으로 깨끗**하다 | 전무 |

> 이것이 §10 우선순위와 §11 로드맵 T1의 설계 근거다.

## §3 나무·식생 — [최소 노력 대비 최대 효과: ★★★☆☆ / 임팩트 최상, 비용 중상]

### 3.1 왜 지금 가짜로 보이는가

**[측정]** `scene_common.py:789 build_tree()` = **눌린 Sphere 11개 + Cylinder 2개**. 끝.

감독 진단이 픽셀 레벨에서 확인한 결함과 대조:

| 결함 | 원인 (코드 레벨) |
|---|---|
| 수관이 완전 불투명한 매끈한 구 껍질 | Sphere 프리미티브 + 불투명 OmniPBR |
| 잎 실루엣 0, 하늘 투과 0 | 알파 채널 자체가 없음 |
| 중첩 구의 교차선(seam) 노출 | 블롭들이 그냥 겹쳐 있고 CSG/블렌딩 없음 |
| translucency 0 | OmniPBR 기본값, 역광 잎 투과 없음 |
| **잎새 얼룩빛(dappled light) 전무** | **불투명 구가 만드는 그림자는 균질한 검은 타원** |
| 헤지 = 등간격 반복(성벽 흉벽) | `build_hedge()`가 동일 반구를 등간격 배치 |

**가장 중요한 것은 마지막 두 줄이다.** 실제 공원 사진에서 가장 강한 시각 신호는 나무 자체가 아니라
**잎 사이로 새는 얼룩빛**이다. 불투명 구는 이걸 물리적으로 만들 수 없다.
그리고 우리 태스크에서 나무 그림자는 **낙차 판단을 교란/보조하는 조명 단서(단서계열 ④)**이므로
이건 룩 문제가 아니라 **태스크 유효성 문제**다.

### 3.2 사실적으로 만드는 실제 기법 (업계 표준)

프로 환경아트의 나무 저작은 다음 계층으로 구성된다:

1. **줄기·주가지 = 실제 메시** (튜브, 8~12각 단면, 테이퍼, 분기점 스무딩)
2. **잔가지+잎 = 알파 카드 클러스터**
   - 잎 여러 장 + 잔가지 하나를 **한 장의 텍스처 아틀라스**에 렌더/촬영해 굽는다
   - 그 카드를 가지 끝에 수십~수백 장 배치 → 실루엣이 자연스럽게 부서진다
3. **노멀 전이(normal transfer)** ← **가장 중요한 트릭**
   - 잎 카드의 노멀을 카드 자체 평면 노멀이 아니라, **수관을 감싸는 가상의 구/타원체 노멀**로 덮어쓴다
   - 효과: 카드 하나하나가 평평하게 번쩍이지 않고 **수관 전체가 하나의 부드러운 덩어리로 셰이딩**된다
   - 이 처리를 안 하면 잎 카드를 써도 "종이 조각 뭉치"로 보인다
4. **양면 투과(two-sided translucency / thin-walled SSS)**
   - 역광 잎이 밝게 비쳐야 한다. 이게 없으면 잎이 플라스틱이 된다
5. **LOD / 원거리 빌보드** — 우리는 정지 이미지라 우선순위 낮음
6. **바람** — 정지 이미지라 **불필요** (모션블러 쓸 때만)

**거리별 요구 수준 [추정, 업계 통념]**
- 근경(0~5 m): 개별 잎 실루엣·잎맥·투과가 보여야 함
- 중경(5~20 m): 수관 덩어리의 **밀도 변주와 하늘 투과 구멍**이 핵심
- 원경(20 m~): 실루엣과 **대기원근(색 탈채도+명도 상승)**이 전부. 형상 디테일 무의미

### 3.3 우리 스택에서의 구현

**경로 A — 외부 에셋 임포트 (권장, 최단)**
```
CC0/무료 나무 .fbx|.glb  →  Isaac Asset Converter  →  instanceable .usd
                          →  scene_common.build_tree() 내부를 add_ref()로 교체
```
- `build_tree()`의 **시그니처를 그대로 유지**하고 내부만 갈아끼우면 33씬 무수정 [측정: 시그니처가
  `(stage, prefix, cx, cy, gz, wood_mtl, canopy_a_mtl, canopy_b_mtl, ...)`이라 재질 인자만 무시하면 됨]

  결정 → 기존의 "같은 씬 재실행 시 동일" 결정성 보존

  Fractional Cutout Opacity를 켜야 함 [확인]

**경로 B — Blender에서 자체 생성**
- Sapling Tree Gen(Blender 내장 애드온)으로 줄기/가지 골격 생성 → 잎 카드를 Geometry Nodes로 산포
  → 노멀 전이(Data Transfer 모디파이어) → USD 익스포트
- 장점: 수종별 파라미터를 우리가 통제 / 단점: 룩 튜닝에 시간이 든다

**경로 C — 지금 당장의 응급처치 (반나절, 스택 무관)**
현행 구 뭉치를 유지하되:
1. **수관 재질에 알파 컷아웃 잎 텍스처**를 물려 구 껍질에 구멍을 뚫는다 → 하늘 투과 + **얼룩빛 그림자 발생**
2. `diffuse_tint` 채도를 낮춘다 (scene04 sat 0.476 → 0.20 목표)
3. 블롭별 tint를 개체 단위로 지터 (현재 2색 랜덤 → 연속 지터)

> **경로 C는 "구를 그대로 두고도 dappled light를 얻는" 유일한 방법이며, 투입 대비 효과가 압도적이다.
> 경로 A 전에 반드시 먼저 한다.**

### 3.5 헤지·관목 (별도 취급 필요)

**[측정] 정정 — `build_hedge()`는 이미 v6에서 개선돼 있다.** 현재 구현은 단일 박스가 아니라
"본체 박스(0.72h) + 상단 crown 블롭 열(좌표 해시 시드, ±6% 요철, 폭 넓으면 2~3열 엇갈림)"이며,
v6 판정 C-5("건초 더미/흙벽돌 상자")에 대한 대응으로 들어간 것이다.

그럼에도 scene04·scene17 렌더에서 **여전히 성벽 흉벽(crenellation) 패턴으로 읽힌다.**
원인을 코드에서 좁히면:

| 잔존 원인 | 코드 근거 |
|---|---|
| **블롭 피치가 완전 등간격** | `pitch = L / n` — 위치 지터가 없다. 크기만 지터되고 **간격은 수학적으로 균일** |
| **알파 실루엣 0** | 블롭이 불투명 타원체 → 윤곽선이 매끄러운 곡선. 실제 헤지 윤곽은 잔가지로 **부서져** 있다 |
| **재질이 평평한 고채도 녹색** | `tint=(0.35,0.45,0.28)` 상수 + grass 텍스처. 개체 단위 색 변이 0 |

→ **처방 수정**: 형상을 갈아엎을 필요는 없다(이미 했다). 남은 것은
1. **[즉시·최저비용]** `pitch`에 ±15~25% 위상 지터 추가 — **1~2줄 수정** [측정: `t0 + (i+0.5)*pitch` 형태에 rnd 오프셋 가산]
2. **[즉시]** 수관과 동일한 **알파 컷아웃 잎 텍스처**를 헤지 재질에도 물린다 → 윤곽 부서짐 + 채도 저하
3. **[중기]** 블롭별 tint 지터

> **교훈**: v6에서 "형상"은 고쳤으나 **"재질(알파·채도)"은 손대지 않아** 개선이 렌더에 안 나타났다.
> §3.3-C(알파 컷아웃)가 나무뿐 아니라 헤지에도 그대로 적용돼야 하는 이유다.

## §4 잔디·지피 — [최소 노력 대비 최대 효과: ★★★★☆ / 임팩트 상, 비용 하~중]

### 4.1 왜 지금 가짜로 보이는가

**[측정]** 잔디 지오메트리 **0개**. 평면에 `aerial_grass_rock` 4K 텍스처만.

결정적 결함은 텍스처 품질이 아니라 **실루엣**이다:
- 잔디밭과 포장의 경계, 잔디밭과 하늘/물의 경계가 **면도날 같은 직선**이다
- 실제 잔디는 어떤 경계에서도 **1~5 cm 스케일의 삐죽한 노이즈 실루엣**을 만든다
- scene17 렌더에서 제방 상단 경계가 완벽한 직선인 것이 이 결함의 교과서적 예다

### 4.2 사실적으로 만드는 기법

1. **잔디 카드(십자/삼중 교차 quad) 또는 메시 블레이드 인스턴싱**
   - 카드: 폴리곤 저렴, 알파 필요, 위에서 보면 들킴
   - 메시 블레이드: 위에서도 견고, 폴리곤 비쌈
   - **우리는 카메라 높이 0.3~1.8 m의 낮은 시점이 대부분 → 카드로 충분** [측정: `grid_views(heights=(0.3,0.9,1.8))`]
2. **밀도 맵**: 균일 산포 금지. 답압(밟힘) 경로는 밀도 0~낮음, 가장자리·구조물 밑동은 높음
3. **개체 단위 색·높이·회전 지터** — 이게 없으면 "인조잔디 카펫"
4. **지면 텍스처와의 블렌딩**: 잔디 카드 밑동 색 = 지면 텍스처 색과 근사해야 함. 아니면 카드가 떠 보임
5. **원거리 페이드**: 일정 거리 이상에서 카드를 지우고 텍스처만 남긴다 (성능+에일리어싱)
6. **경계 침입**: 포장 가장자리·균열로 잔디/잡초가 **비집고 나오게** 한다 → §8과 연동

### 4.3 우리 스택에서의 구현 — `UsdGeom.PointInstancer`

**[확인] PointInstancer는 설계상 수십억 인스턴스를 목표로 하며 인스턴스당 32바이트**
(position float3 + orientation quath + scale float3)만 쓴다.

우리 코드에 이미 있는 것과 붙이기:

                  z_fn, seed, exclude_polys=()):

    # 2) exclude(포장·계단) 영역 제외 + 경계 근처 밀도 페이드

**4090 24 GB 예산 계산 [추정]**

| 항목 | 값 |
|---|---|
| 인스턴스 데이터 | 32 B/개 → **100만 개 = 32 MB** (무시 가능) |
| 실제 병목 | 프로토타입 메시의 BVH + 알파 텍스처 |
| 잔디 카드 1개 | 3 quad = 6 tri 가정 |
| 100만 인스턴스 | 600만 tri 상당 — **PT에서 충분히 감당** [추정] |
| 커버 면적 | 밀도 400개/m² × 2,500 m² = 100만 개 → 50 m × 50 m 잔디밭 |

→ **씬당 잔디 인스턴스 예산 100만 개를 상한으로 잡는다.** 카메라 20 m 밖은 밀도를 1/4로 떨어뜨리고
40 m 밖은 텍스처만 남기면 실사용은 30~50만 개 선에서 끝난다 [추정].

> **주의: PointInstancer 인스턴스에는 콜라이더를 걸지 말 것.** [확인] Isaac Lab 이슈 #1218에서
> 인스턴서-콜리전 상호작용 문제가 보고돼 있다. 잔디는 시각 전용이므로 문제없다.

### 4.4 최소 노력 버전 (반나절)

전면 인스턴싱 전에, **경계선 실루엣만** 깨도 인상이 크게 바뀐다:
- 잔디-포장 경계를 따라 **폭 20~40 cm 띠에만** 잔디 카드를 인스턴싱 (수천 개 규모)
- 이것만으로 §4.1의 "면도날 직선" 결함이 사라진다 → **투입 대비 최고 효율**

## §5 지면·포장 — [최소 노력 대비 최대 효과: ★★★★★ / 임팩트 최상, 비용 최하]

### 5.1 왜 지금 가짜로 보이는가

**[측정]** 세 가지가 겹쳐 있다:

1. **재질의 71.3%가 상수색** — 텍스처가 아예 없다. `flat%` 56.2%(scene17)의 직접 원인
2. **텍스처가 있어도 단일 타일 균일 반복** — 매크로 변주 0 → 원거리에서 격자 반복 노출
   (scene01 광장 렌더에서 타일 패턴이 화면 끝까지 완벽히 규칙적인 것이 이것)
3. **완전 평면** — 미세 기복·침하·물고임 0. 재질 경계가 **수학적 직선 폴리곤 에지**

### 5.2 사실적으로 만드는 기법

| 기법 | 내용 |
|---|---|
| **매크로 변주** | 파장 10~30 m 저주파 노이즈로 albedo 명도·채도를 ±10~15% 변조 → 반복 파괴의 90%는 이것 하나로 끝난다 |
| **회전 패치 혼합** | 같은 텍스처를 90°/180° 회전해 노이즈 마스크로 섞음 → 격자성 제거 |
| **디테일 노멀** | 근경용 고주파 노멀을 2차로 겹침(타일 크기 5~20 cm) → 근접 촬영에서 픽셀이 죽지 않음. **`flat%` 직격** |
| **재질 블렌딩** | 정점 컬러/하이트 블렌드로 마모 경로·이끼·얼룩을 픽셀 단위 크로스페이드 |
| **전이대(transition zone)** | 자갈↔잔디, 연석↔아스팔트 경계에 폭 10~50 cm의 혼합 대역. **하드 폴리곤 에지는 최대 단서** |
| **미세 기복** | 변위 또는 정점 변형으로 ±1~5 cm. 물고임·침하·바퀴자국 |
| **균열·패치·보수 흔적** | 데칼 또는 마스크. 아스팔트 보수 패치는 색·거칠기가 다르고 **경계가 삐뚤다** |
| **물고임** | 저지대에 roughness→0 + 약간의 albedo 어둡게. 젖은 곳은 **주변보다 색이 진하다** |
| 텍셀 밀도 일관성 | **[확인] 업계 통념: 배경 프롭 ~512 px/m, 히어로 에셋 ~1024 px/m**. 물체마다 제각각이면 즉시 CG로 읽힘 |

### 5.3 우리 스택에서의 구현 — **이미 다 만들어져 있다**

**[측정] `assets/NegObsGround.mdl`이 위 표의 상위 5개를 이미 구현하고 있다.**
(매크로 변주 `macro_amp/macro_wavelength`, 회전 패치 `patch_wavelength`, 재질 블렌딩
`use_blend`+primvar, 전이대 `blend_edge_noise/blend_edge_wavelength`, roughness 노이즈 `rough_noise`)

**따라서 §5의 작업 대부분은 "신규 개발"이 아니라 "적용"이다.**

실행 계획:
1. **`NegObsGround.mdl` → `NegObsSurface.mdl`로 일반화** (지면 전용 가정 제거, 수직면·계단에도 사용 가능하게)
2. `scene_common.make_pbr()`에 `use_negobs=True` 스위치를 추가해 **OmniPBR 대신 이 MDL을 바인딩**
   → 씬 파일 무수정으로 33씬 전체가 매크로 변주·반복 파괴를 얻는다
3. **상수색 610건 처리**: `diffuse_color=`만 있는 재질에 **최소 1장의 텍스처를 강제**한다.
   전용 텍스처가 없으면 범용 콘크리트/금속 디테일 노멀 + 미세 노이즈만이라도 물린다.
   → **이 한 작업이 `flat%`를 가장 크게 떨어뜨린다** [추정: 19.1% → 10% 이하]
4. 미세 기복: **[확인]** `/rtx/material/enableMDLDisplacement` + MDL displacement 함수.
   또는 지면 슬래브를 `UsdGeom.Mesh` 격자(0.5 m 피치)로 바꾸고 정점 Z를 노이즈로 흔든다 —
   **후자가 더 안전하고 빠르다** [추정]. TerrainGen 렌더가 이 방식의 효과를 이미 입증했다
5. 전이대: 지면 메시에 `blend_tw` primvar를 굽고 경계 대역 재질 바인딩 (TerrainGen이 검증한 경로 그대로)

### 5.4 우선순위

> **§5는 전 항목 중 임팩트/비용 비가 가장 좋다.** 이유: (a) 화면 점유 면적이 압도적으로 크고,
> (b) 해법이 이미 사내에 존재하며, (c) 씬 파일을 안 건드리고 `scene_common.py`만 고쳐도 적용되고,
> (d) 감독이 설정한 정량 목표(`flat%`, `slope`)에 직결된다.
> **1주차에 이것부터 한다.**

## §6 계단·난간·연석 — [최소 노력 대비 최대 효과: ★★★★★ / 임팩트 최상, 비용 하]

### 6.1 우선순위 판단 — **결론: 여기가 1순위와 공동 1순위다**

우리 태스크는 **보이지 않는 낙차를 맥락으로 추정**하는 것이고, 단서계열 ①(설비 역추론:
난간·볼라드·점자블록)이 가장 강한 단서다. 즉 **난간과 연석은 우리 네트워크가 실제로 봐야 하는 픽셀**이다.

> 배경 나무가 가짜인 것은 "인상"의 문제지만, **난간이 가짜인 것은 "단서 자체가 가짜"라는 뜻**이다.
> sim2real에서 실패하면 가장 먼저 깨질 부분이다. **투자 우선순위 최상위가 맞다.**

다만 §5와 달리 화면 점유 면적은 작으므로, `flat%` 같은 전역 지표는 별로 안 움직인다.
**정량 지표와 태스크 유효성이 갈라지는 유일한 항목**이므로 지표만 보고 판단하면 안 된다.

### 6.2 왜 지금 가짜로 보이는가

**[측정]** scene01 렌더 육안 감식 + `build_railing_line()` 코드 확인:
- 계단 모서리가 **완벽한 90° 샤프 에지** — 베벨/챔퍼 0건(전 씬)
- 난간 = **`add_cylinder()` 4종(상단레일·중간레일·포스트)이 전부.** 볼트·플랜지·용접부·이음매 0.
  포스트는 `ground_fn(x)`로 얻은 지면 z에 **그냥 꽂힌다** — 베이스 플레이트 없음
- 레일이 **수학적 완전 직선**, 처짐·부정렬 0
- 계단 답면이 **완전 균질** — 통행 마모 0, 논슬립 홈 0
- 점자블록이 노란 상수색 띠 — 돌기 지오메트리는 있으나(`build_tactile` proud=0.004) 재질이 단색

### 6.3 사실적으로 만드는 기법

**(a) 베벨/챔퍼 — 단일 최대 효과**

현실에 **완벽한 샤프 에지는 존재하지 않는다.** 모든 물체의 모서리는 최소 0.5~2 mm 둥글고,
그 곡면이 하이라이트를 잡아 **에지를 한 줄의 밝은 선으로 그린다.** 이 밝은 선이 없으면
뇌가 즉시 "CG"로 판정한다. 업계에서 "모든 에지에 베벨"이 철칙인 이유다.

- 콘크리트 계단 실물: 시공 시 **모따기(챔퍼) 10~20 mm**를 의도적으로 넣는다(모서리 파손 방지)
- 마모된 계단코(nosing): 통행으로 **반경 5~15 mm**까지 둥글어진다
- 금속 난간: 압출 프로파일이라 **1~2 mm** 라운딩

**(b) 계단 고유 디테일**
- **논슬립**: 홈(groove) 2~4줄 또는 삽입 인서트. 한국 공공계단은 **황동/고무 인서트**가 흔하다
- **차등 마모**: 답면 **중앙**은 통행으로 반들반들(roughness↓, 색 밝아짐), **가장자리**는 때가 낀다(어둡다)
- **모서리 파손(chipping)**: 계단코 몇 군데가 깨져 있다. 전부가 아니라 **몇 군데**인 것이 중요
- **줄눈·신축이음**: 일정 간격의 라인. 여기에 때·잡초가 낀다
- **거푸집 자국**: 콘크리트 측면의 판재 이음 라인

**(c) 난간 디테일**
- **용접 비드**: 파이프 접합부의 볼록한 링
- **베이스 플랜지 + 앵커볼트**: 밑동의 사각/원형 판 + 볼트 4개. **이게 없으면 난간이 바닥에 박힌 막대**
- **페인트 벗겨짐**: 손이 닿는 상부 레일과 모서리에서 벗겨진다 (커비처 기반)
- **녹 흘림(rust runoff)**: 볼트·용접부에서 **아래로** 흐른 갈색 줄. **방향이 중요하다 — 항상 중력 방향**
- **미세 부정렬**: 지주가 몇 mm 기울거나 레일이 살짝 처진다. 완벽한 직선은 가짜다

**(d) 접지부(contact) — 모든 물체 공통**
바닥과 만나는 모든 선에 **어두운 띠**가 있어야 한다: AO + 먼지 퇴적 + 그라우트.
이게 없으면 물체가 바닥 위에 **떠 있는 것처럼** 보인다 (scene01 난간이 정확히 이 증상).

### 6.4 우리 스택에서의 구현

**[확인] 최고의 소식: 지오메트리를 안 고치고 베벨을 얻을 수 있다.**

Omniverse RTX 106.1이 **MDL 라운디드 코너**를 RT/PT 양쪽에서 지원한다.
`state::rounded_corner_normal(radius, across_materials, roundness)`는 **노멀만 수정**하므로
`UsdGeom.Cube` 그대로 두고 셰이딩만 둥글게 만든다.

```
NegObsSurface.mdl 안에서:
  geometry: material_geometry(
      normal: state::rounded_corner_normal(
                  radius: rounded_radius,      // 0.002 ~ 0.015 m
                  across_materials: true,
                  roundness: 1.0))
```

→ **`make_pbr()`에 `rounded_radius` 인자 하나를 추가하고 기본값을 2 mm로 주면,
33씬의 모든 Cube/Cylinder가 즉시 베벨을 얻는다.** 씬 파일 수정 0.
**이것이 본 보고서 전체에서 투입 대비 효과가 가장 높은 단일 작업이다.**

나머지 구현:

| 항목 | 방법 | 난이도 | 현행 상태 |
|---|---|---|---|
| 베벨/챔퍼 | MDL rounded corner (위) | **하** | **없음** |
| 논슬립 띠 | `build_nosing()` **이미 존재** — 단, `diffuse_color` 상수색(황색)이라 평평하다. **텍스처+마모 부여만 하면 됨** | **하** | 형상 O / 재질 ✕ |
| 점자블록 | `build_tactile()` **이미 존재** (proud=0.004, 돌기는 노멀맵 전제). 렌더에서 단색 노란 띠로 보이는 것은 **노멀맵이 안 물린 재질을 넘겨서** [추정] — 검증 필요 | **하** | 형상 O / 재질 의심 |
| 차등 마모 | 답면 중앙/가장자리 roughness 구배 — 트라이플래너 + 로컬 UV 기반 마스크 | 중 | 없음 |
| 모서리 파손 | 소형 Cube를 랜덤 몇 곳에 불리언 대신 **덧대기**(색 다른 파손면) | 중 | 없음 |
| 용접 비드 | 접합부에 얇은 Cylinder(약간 큰 반경) 삽입 | **하** | 없음 |
| 베이스 플랜지+볼트 | 얇은 Cube + Cylinder×4. `build_railing_line()` 포스트 하단에 추가 | **하** | 없음 |
| 레일 부정렬 | 포스트 z·xy에 ±3 mm 해시 지터 (기존 좌표 해시 패턴 재사용) | **하** | 없음 |
| 녹 흘림 | MDL: 볼트 높이 아래 world-Z 감쇠 마스크 × 수직 스트리크 노이즈 | 중 | 없음 |
| 접지 AO/오염 | MDL: world-Z가 지면 근처일 때 albedo 감쇠 (`smoothstep(0, 0.15, z-z_ground)`) | **하** | 없음 |

> **[측정] 반가운 사실: 논슬립 띠와 점자블록은 형상이 이미 만들어져 있다.**
> 즉 §6의 상당 부분은 "새로 만들기"가 아니라 **"이미 만든 형상에 제대로 된 재질을 물리기"**다.
> 이는 §5.3의 "상수색 610건" 작업과 **같은 작업**이다 — 한 번에 처리된다.

> **주목: "용접 비드", "베이스 플랜지+볼트", "접지 오염"은 전부 난이도 '하'인데
> 난간을 진짜처럼 보이게 하는 효과는 크다.** `build_railing_line()` 한 함수만 고치면
> 난간이 나오는 모든 씬에 일괄 적용된다.

## §7 건물 파사드 — [최소 노력 대비 최대 효과: ★★★☆☆ / 임팩트 중, 비용 중]

### 7.1 왜 지금 가짜로 보이는가

**[측정]** scene01 렌더: 벽돌 텍스처 박스 + **표면에 붙은 납작한 파란 사각형**이 창문.

### ⚠ 발견: `window["inset"]`은 8개 씬이 넘겨주지만 아무도 읽지 않는다 (미구현 파라미터)

```python
# scene_common.py:891 — 기본값에 inset 정의
window = dict(w=1.2, h=1.6, inset=0.15, col_step=2.5, margin=2.0)

# scene_common.py:906 — 그러나 창 배치는 inset을 무시하고 파사드 +5 mm 에 놓는다
gy = bd["facade_y"] + bd["face_dir"] * 0.005
... add_box(..., (xc, gy, zc), (wd["w"], 0.03, wd["h"]), glass_mtl)
```

**[측정] `wd["inset"]`은 `build_building()` 본문 어디에서도 참조되지 않는다.**
그런데 scene01·02·06·08·12 등이 전부 `inset=0.15`를 성실히 넘겨주고 있다.
즉 **"창을 15 cm 안으로 넣겠다"는 설계 의도는 처음부터 있었고, 구현만 누락됐다.**

게다가 현재 창은 들어가 있기는커녕 `face_dir * 0.005`로 **파사드에서 5 mm 튀어나와 있다.**
= 벽에 붙인 파란 스티커.

**창의 개구부 깊이 0이 단일 최대 결함이다.** 실제 창은 벽 두께만큼(10~25 cm) 들어가 있고
그 그림자가 파사드에 리듬을 만든다. 이게 없으면 건물이 **판때기 세트**로 보인다.

> **이 수정의 비용은 사실상 0이다** — 이미 모든 호출부가 인자를 넘기고 있으므로
> `build_building()` 안에서 `gy = bd["facade_y"] - bd["face_dir"] * wd["inset"]`로 바꾸고
> 프레임 Cube 4개를 두르면 끝난다. **§10 우선순위 ⑧의 비용을 1 → 0.5로 하향한다.**

나머지 결함:
- 창틀·멀리언 없음 (창이 두께 3 cm 판 하나)
- 유리 반사 없음, 내부 암부 없음 → 파란 페인트 조각
- 층 분절·물끊기 없음 (**파라펫은 이미 있다** — `/Parapet` 프림 존재. 정정)
- 한국 도시 특징(실외기·배관·간판·전선) 전무

### 7.2 사실적으로 만드는 기법

1. **모듈러 파사드 킷**: 층/베이 단위 모듈(창+벽+슬래브)을 정의하고 반복 배치. 우리 절차생성과 궁합 최상
2. **개구부 깊이(reveal)**: 창을 벽면에서 **10~25 cm 안으로** 밀어넣는다
3. **창틀·멀리언**: 프레임 두께 4~8 cm, 분할 바
4. **유리 셰이딩**: 낮은 roughness + 높은 반사 + **어두운 내부 색**. 층마다 반사 각도가 달라야 함
5. **내부 암시**: 커튼/블라인드를 다른 밝기·색으로 랜덤. 이게 있으면 건물이 "사람이 사는 곳"이 된다
6. **층 분절**: 슬래브 라인, 발코니, 난간
7. **파라펫 + 물끊기**: 옥상 난간벽. 그 아래로 **빗물 오염 줄**이 흐른다
8. **한국 도시 시그니처** (우리 씬의 정체성을 만드는 요소):
   - **실외기**: 창 옆·발코니에 박스 + 그릴. 층마다 위치가 미묘하게 다름
   - **외부 배관·가스관**: 벽면을 수직으로 타고 내려오는 노란 가스배관 (매우 한국적)
   - **옥상 물탱크**, 옥탑방
   - **간판**: 저층부에 밀집. 크기·색·높이가 제각각
   - **전선·통신선**: 전신주 사이를 늘어져 지나감 (현수선 curve)
   - **방범창**: 저층 창의 격자
   - **어닝/차양**

### 7.3 우리 스택에서의 구현

`scene_common.py:883 build_building()`을 확장한다. 전부 Cube/Cylinder로 가능하다:

| 항목 | 구현 | 난이도 |
|---|---|---|
| 개구부 깊이 | 창 Cube를 벽면 −0.15 m로 이동 + 사방에 프레임 Cube 4개 | **하** |
| 유리 재질 | `make_pbr(roughness_const=0.05, metallic=0, specular_level=0.9, diffuse_color=어두운 청회색)` | **하** |
| 층별 창 변주 | 좌표 해시로 커튼 유무·밝기 랜덤 | **하** |
| 실외기 | Cube + 전면 그릴(얇은 Cube 반복). 창당 60% 확률 배치 | 하 |
| 가스배관 | 노란 Cylinder 수직 + 엘보 | **하** |
| 파라펫 | 옥상 테두리 Cube | **하** |
| 간판 | `build_sign()` 재활용 + 저층부 밀집 배치 | 중 |
| 전선 | Cylinder 체인으로 현수선 근사 (또는 `UsdGeom.BasisCurves`) | 중 |
| 오염 줄 | MDL: 창 하단·파라펫 아래 수직 스트리크 (§8) | 중 |

> **우선순위 판단: 건물은 우리 태스크에서 "배경"이다.** 낙차 단서로서의 기여는
> 스케일 앵커(창 크기 = 층고 3 m)와 원근 정도. **§5·§6보다 뒤에 둔다.**
> 단 **개구부 깊이 + 유리 재질(둘 다 난이도 '하')**은 효과 대비 너무 싸서 1주차에 끼워 넣는다.

## §8 웨더링·엔트로피 — [최소 노력 대비 최대 효과: ★★★★☆ / 임팩트 상, 비용 중]

### 8.1 왜 지금 가짜로 보이는가

**엔트로피가 0이다.** 모든 표면이 새것이고, 모든 물체가 완벽히 정렬돼 있고, 아무것도 떨어져 있지 않다.
현실의 시각적 복잡성 대부분은 **시간이 남긴 흔적**에서 온다.

### 8.2 절차적 웨더링의 핵심 — 마스크 생성 규칙

웨더링을 "손으로 그리는" 대신 **기하로부터 마스크를 계산**한다. 이것이 Substance 계열
스마트 머티리얼의 작동 원리이며, MDL로 그대로 옮길 수 있다.

| 마스크 소스 | 물리적 의미 | 만들어내는 효과 |
|---|---|---|
| **커비처(볼록)** | 돌출 모서리 = 물리적 접촉·마찰 | **에지 마모** — 페인트 벗겨짐, 콘크리트 백화, 금속 광택 |
| **커비처(오목)/AO** | 오목부 = 물이 고이고 먼지가 쌓임 | **크레비스 더트** — 줄눈·구석의 검은 때 |
| **월드 Z (아래로 감쇠)** | 지면 근처 = 흙탕물 튐 | **접지 오염대** — 벽 하단 0~40 cm |
| **월드 Z (위에서 아래로 흐름)** | 중력 | **빗물 오염 줄(streaking)** — 항상 아래 방향, 돌출부 아래에서 시작 |
| **노멀 상향(N·Z)** | 위를 보는 면 | **먼지·이끼·낙엽 퇴적**, 눈 쌓임 |
| **노멀 수직** | 벽면 | **흘러내린 자국** |
| 월드 위치 노이즈 | — | 얼룩의 불규칙성 |

**규칙 예시 (MDL 의사코드)**
```
dirt_ground  = smoothstep(0.45, 0.0, z_above_ground)          // 밑동 오염
streak       = streak_noise(x, y) * smoothstep(z_top, z_top-2.0, z)  // 수직 흘림
edge_wear    = curvature_convex ^ 2
crevice      = (1 - ao) * 0.7
moss         = n_up * wetness_map * shade_map                  // 위·습·그늘
albedo = base
       * lerp(1, 0.55, dirt_ground)
       * lerp(1, 0.7,  streak)
       * lerp(1, 1.35, edge_wear)      // 마모부는 밝게(백화) 또는 하지색
       * lerp(1, 0.5,  crevice)
```

### 8.3 우리 스택에서의 구현

**MDL에서 커비처/AO를 직접 얻기는 어렵다** [추정 — MDL 표준에 커비처 질의가 없음].
현실적 대안 3가지, 비용 순:

1. **[최저비용] world-Z 기반만 쓴다.** 접지 오염·수직 흘림·먼지 퇴적은 전부 z와 노멀만으로 계산 가능하다.
   **이것만으로도 엔트로피 인상의 절반 이상을 얻는다.** `NegObsSurface.mdl`에 인자 몇 개 추가.
2. **[중간] 정점 primvar로 굽는다.** 씬 조립 시 파이썬에서 각 정점의 "에지 근접도"를 계산해
   primvar로 쓴다. 우리는 지오메트리를 코드로 만들므로 **모서리가 어디인지 이미 안다** — 오히려 쉽다.
   `NegObsGround.mdl`이 이미 `scene::data_lookup_float`로 primvar를 읽는 코드를 갖고 있다.
3. **[고비용] Blender에서 텍스처로 굽는다.** 부품 에셋에만 적용.

**소품 엔트로피 (지오메트리)** — PointInstancer로 산포:
- 낙엽(계절), 잔가지, 담배꽁초, 낙엽 더미(구석에 몰림), 잡초(균열·줄눈에서), 이끼 패치
- **배치 규칙이 핵심**: 무작위 균등 산포는 오히려 가짜다. **구석·모서리·바람 그늘에 몰려야 한다**
- 우리 배치1이 이미 낙엽(C2)·눈(C1)·젖음(C4) 변주를 갖고 있으므로 그 코드를 일반화

### 8.4 채도 캘리브레이션 (별항)

**[측정] 감독 진단: 우리 sat 0.298 vs 실사 0.158 — 1.9배 과채도.** scene04는 0.476.

웨더링의 부수 효과 중 하나가 **탈채도**다. 실제 도시 표면은 먼지·풍화로 채도가 낮다.
- 즉시 조치: 모든 `tint`/`diffuse_color`의 채도를 일괄 0.6~0.7배 → **한 줄 변경으로 전 씬 적용 가능**
- 근본 조치: 웨더링 마스크가 albedo를 회색 쪽으로 끌어당기게 설계
- **대기원근 추가**: 원거리 객체를 하늘색 쪽으로 lerp — 원경 채도 저하 + 깊이감. scene17처럼
  원경이 넓은 씬에 특히 유효

## §9 동적 개체(사람·차량) — [최소 노력 대비 최대 효과: ★★★☆☆ / 임팩트 중상, 비용 중]

### 9.1 넣어야 하는가 — **판정: 넣어야 한다. 단 3순위.**

**찬성 근거 (강함)**
- 우리 단서계열 ③이 **스케일 앵커**다: "수관·차 지붕·사람 상반신이 눈높이 이하면 아래가 꺼져 있다".
  **이 단서는 사람/차량이 씬에 없으면 학습 자체가 불가능하다.**
- 즉 사람·차량은 "장식"이 아니라 **태스크 정의에 포함된 단서 객체**다.
- 실제 보행 환경 사진에는 거의 항상 사람이나 차가 있다 → 없으면 sim2real 도메인 갭

**신중론**
- GT 라벨링 복잡도 증가
- 사람 에셋의 라이선스가 까다롭다(§9.3)
- 나쁜 인체 에셋은 오히려 "게임"감을 **증폭**시킨다 — 어설픈 마네킹은 없느니만 못하다

**결론**: **단서계열 ③을 검증하는 씬(제방·주차장·육교 등 스케일 앵커가 핵심인 씬)에 우선 투입**하고,
전 씬 일괄 배치는 하지 않는다. 품질 미달 에셋이면 **차량만 넣는다**(차량은 강체라 실패 위험이 낮다).

### 9.2 배치 전략

- **사람**: 서 있기·걷기 위주. 카메라와 5~25 m. **얼굴 디테일 불필요**(원경이므로) — 실루엣과 크기가 전부.
  낙차 경계 **너머**에 배치하면 상반신만 보이는 앵커가 된다 (= 우리가 원하는 바로 그 단서)
- **차량**: 주차장·도로 씬. 지붕 높이 ~1.45 m(승용) / ~2.0 m(SUV·승합)가 앵커
- **자전거·킥보드**: 한강·공원 씬. 저비용 고효과 [추정]
- **그림자·접지 필수**: 접지 그림자 없는 인물은 즉시 합성 티가 난다

### 9.3 라이선스 주의 (매우 중요)

인체 에셋은 라이선스가 함정이다. **논문에 렌더 이미지를 싣고 데이터셋을 공개할 수 있는가**가 기준이다.

- **SMPL/SMPL-X 계열**: 학술 연구용과 상업용 라이선스가 분리돼 있다. 데이터셋 공개 조건을 반드시 확인
- **Mixamo**: 무료·리깅 제공이나 라이선스 조항 확인 필요
- **MakeHuman/MPFB2**: CC0 지향으로 알려져 있어 가장 안전한 후보 [추정]
- **Daz3D**: EULA가 까다로운 것으로 유명 — **회피 권장**
- **Fab**: "any engine or tool" 허용이나 **단독 재배포 금지** → 렌더 이미지 공개는 OK, USD 씬 배포는 위험

> 구체 목록과 검증된 라이선스 조항은 §12(부록)에 정리.

| D3 | 상수색 610건 감사 → 범용 디테일 노멀·미세 노이즈 일괄 부여. 채도 0.65배 적용 | 스크립트 1개 |

| D6-7 | **scene04·scene17·scene01 3씬만 재렌더 → `imgstats.py` 재측정 → 목표 미달 시 튜닝** | before/after 비교 |

**전 씬 재렌더는 이 게이트를 통과한 뒤에만 한다** (GPU 1대, 렌더 병렬 금지이므로 비싸다).

### 로드맵 원칙 3가지

1. **씬 파일을 건드리는 작업은 최대한 뒤로 민다.** v5 21/21 합격 자산을 지키는 것이 최우선.
2. **매 단계마다 `imgstats.py`로 정량 검증한다.** 감독이 before 기준선을 만들어 뒀으므로
   개선을 주관이 아니라 수치로 증명한다.
3. **전 씬 재렌더는 게이트 통과 후에만.** GPU 1대·PT 수백 프레임 누적이므로 재렌더가 가장 비싸다.

## §12 부록 — 에셋 소스 및 라이선스

### 12.1 우리는 이미 CC0 조달 파이프라인을 갖고 있다 [측정]

새로 만들 필요가 없다. `assets/download_assets.py`가 이미:
- **PolyHaven API** (`https://api.polyhaven.com/files/{slug}`) — CC0. 텍스처 4K jpg + HDRI 4K exr.
  재실행 시 스킵·재시도 3회·크기 검증 내장. **함정 기록됨**: PolyHaven이 기본 urllib UA를 403 차단
  → 스크립트에 UA 헤더 포함 완료
- **ambientCG** — CC0. v6에서 `PavingStones015`(2K-JPG, Color/NormalDX/Roughness)로 교체한 이력
- **자체 생성** — `assets/signs/gen_signs.py`가 한글 사인 텍스처를 절차 생성

그리고 `scene_common.py`의 `TEX` 레지스트리가 역할명 → 파일 경로를 매핑하므로,
**새 텍스처를 추가하는 비용이 이미 매우 낮다.** §5.3의 "상수색 610건에 텍스처 부여"가
현실적인 이유가 이것이다.

> **확장 방향: 이 파이프라인을 "텍스처"에서 "메시 + 데칼"로 넓히기만 하면 된다.**

## §13 이 보고서의 한계

- **[추정] 표시 항목은 검증되지 않았다.** 특히 잔디 인스턴스 예산, `flat%` 개선 폭 추정치,
  MDL 커비처 부재 판단은 실제 테스트로 확인해야 한다.
- **MDL 라운디드 코너의 실제 육안 효과를 우리 씬에서 검증하지 않았다.** 릴리스 노트상의 기능 존재만
  확인했다. T1 D1에서 **가장 먼저 스파이크 테스트**할 것을 권한다 — 이 기능이 기대대로 동작하지 않으면
  우선순위 1번이 무너지므로.
- 렌더 시간·GPU 메모리 실측을 하지 않았다. PointInstancer 100만 개의 실제 PT 렌더 비용은 미지수.
- Infinigen을 **실제로 설치해 보지 않았다.** 판정은 공식 문서·논문 기반이다. 다만 "자연물 전용"과
  "나무 익스포트 미지원"은 1차 출처에서 명확히 확인됐으므로 판정을 뒤집을 여지는 작다 [추정].
- **§12.4의 에셋 라이선스 조사가 미완이다.** 인체·차량·나무 에셋 소스는 별도 확인이 필요하다.
  단 §11 T1(1주차) 계획은 외부 에셋에 의존하지 않도록 설계했으므로 착수에 지장은 없다.
