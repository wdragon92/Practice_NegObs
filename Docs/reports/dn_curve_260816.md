## 0. 헤드라인 (결재가 필요한 두 줄)

1. **5점 곡선은 성립하지 않는다 — spp 축이 캡처 이미지에 도달하지 않는다.**
   디노이저 OFF 3팔(spp 64·128·256)의 **노이즈가 완전히 동일**하다(잔차 sd
   0.0230 / 0.0230 / 0.0228). 렌더 시간은 spp 에 비례해 늘었는데(5.0 → 9.1 →
   14.9 s/컷) 픽셀 노이즈는 1/√spp 로 **전혀 줄지 않았다**. 곡선은 사실상
   **2점(디노이저 ON/OFF)** 이다.
2. **디노이저 판정**: OFF 가 slope 를 자연영상 쪽으로 **+0.135** 되돌리지만
   평탄면 노이즈를 **23배** 키운다. 그리고 ①의 결과로 **"OFF + spp 증량으로
   노이즈를 되사는" 선택지는 현재 파이프라인에 존재하지 않는다.** 따라서
   spp 배선을 고치기 전까지 디노이저 OFF 채택은 **권고하지 않는다**.

## 3. spp 축 무효 — 근거

동일 설정 두 팔의 **픽셀 차분** 표준편차(하위 45 % 대역):

| 쌍 | std(차분) |
|---|---|
| C−D (64 vs 128) | 0.01588 |
| D−E (128 vs 256) | 0.01574 |
| C−E (64 vs 256) | 0.01581 |
| A−B (ON, 256 vs 64) | 0.00811 |

노이즈가 1/√spp 로 준다면 std(C−D) : std(D−E) 는 **1.41 : 1** 이어야 한다.
실측 **1.009 : 1** — 세 팔은 **같은 노이즈 수준의 서로 다른 난수 실현**일 뿐이다.
md5 는 전부 다르므로 "같은 파일 복사"는 아니다(별개 렌더가 맞다).

**시간은 spp 에 비례해 늘었다**(5.0 / 9.1 / 14.9 ≈ 1 / 1.8 / 3.0 = 64 / 128 / 256).
즉 렌더러는 샘플을 **실제로 소비했는데 캡처된 프레임에는 반영되지 않았다.**

배선 지점: `scene_common.py:4937-4943` — `NEGOBS_PT_TOTAL_SPP` →
`/rtx/pathtracing/totalSpp`, 그리고
`warmup = max(8, ceil(tot / (spp16 × subframes8)))`.
tot 64·128·256 모두 **warmup 이 8 로 동일**하게 계산된다(ceil(256/128)=2 < 8).
유력 가설(미확정): 프레임마다 누적이 초기화되어 캡처 프레임은 항상
`spp16 × subframes8 = 128 샘플` 한 프레임분이고, `totalSpp` 는 프레임당 작업량만
늘린다. **확정하려면 `/rtx/pathtracing/totalSpp` 실효값과 누적 카운터를
런타임에서 찍어봐야 한다 — 본 측정 범위 밖.**

> 부수 결함: 이 3팔의 `round_stamp.json` 은 `"env": {}, "env_captured": false` —
> **어떤 spp 로 렌더했는지 기록이 없다.** spp 값의 유일한 근거가 라운드 *이름*이다.
> 라운드 규약 X2(정직한 meta)의 구멍. 앞으로 렌더 env 는 스탬프에 박아야 한다.

## 4. 결론 및 권고

- **디노이저 OFF 채택 = 보류 권고.** slope 이득 0.135 는 실재하나, 대가가
  평탄면 노이즈 23배이고 **spp 로 상쇄할 수단이 현재 작동하지 않는다.**
- **선행 과제**: spp 배선 결함 확정·수리(§3). 고친 뒤 OFF 팔을 spp 256/512 로
  다시 찍으면 그때 비로소 진짜 5점 곡선과 "노이즈 대 slope" 교환곡선이 나온다.
- GT-127 의 "slope 잔여 격차의 실소유 = 렌더 설정층" 판정은 **유지**된다.
  다만 그 층의 노브가 디노이저 하나가 아니라 **디노이저 + (고장난) spp** 라는 것이
  이번에 드러났다.
