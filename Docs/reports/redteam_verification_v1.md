## §1 판정 요약

**담보하는 것.** 감독의 절차는 "코드가 크래시 없이 돌고, 내가 고른 1개 씬의
1개 카메라에서 의도한 형상이 화면에 나타난다"는 것을 담보한다. 이건 사소하지
않다 — `18c8643` 에서 실제로 크래시 2건(`xformOpOrder` 중복, 상한 절단으로 피복
0.07)을 렌더가 잡아냈고, 이는 렌더 없이는 못 잡았을 버그다. 커밋 메시지의
정량 주장 중 검산 가능한 것 다수(낙엽 845개, mean_cov 0.0435, 실측 삼각형·유효
면적표 4/5행)는 **재계산에서 정확히 재현된다**. 감독이 수치를 지어내지 않는다는
점은 이 감사에서 확인됐다(§4).

**담보하지 못하는 것.** 절차가 담보하지 못하는 것은 네 가지이고, 넷 다 이번
3커밋에서 실제로 사고로 이어졌다. ① **커버리지** — 간살 코드는 17개 씬이 쓰는데
sceneC2 1개만 렌더했고, sceneC2 의 `ground_fn` 은 이 함수를 쓰는 씬 중 소수인
**연속 함수**다. 다수파인 계단식 `ground_fn` · `x_top==x_start` · `drop==0` ·
자체 세로살 보유(scene10) 경로는 한 번도 실행되지 않았다. ② **대조군 오염** —
감독이 만든 비교 시트 3장의 "기존" 은 전부 `r2_on`(23:04) 이다. 그 사이에
커밋이 3~5개 들어 있어, 한 변경의 효과라고 제시된 화면 차이가 실은 나무 에셋
교체·건물 v2·화단 수정·간살·낙엽의 합이다. 단일 변수 A/B 가 아니다. ③ **수치
부재** — 감독은 `scripts/imgstats.py` 와 `scripts/regression_check.py` 를 갖고
있으면서 3커밋에서 **한 번도 돌리지 않았다**(3커밋의 변경 파일 목록에 측정
산출물 0건). 내가 그의 도구를 그의 렌더에 돌리자 **자기 도구가 FAIL 1 · WARN 4
를 뱉는다**(§3 R1). ④ **육안이 못 보는 축** — 프림 예산, 인스턴싱 무효화,
`0.15 m` 유한차분이 계단에서 반환하는 값 같은 것은 원리적으로 눈에 안 보인다.
그중 하나(인스턴싱)는 **직전 커밋에서 감독 자신이 넣은 최적화를 다음 커밋이
무효화한 것**인데, 두 커밋 모두 "검증 완료" 로 보고됐다.

## §3 재현 가능한 반증

각 항목은 "이 명령 → 이 값" 형식이다. 모두 GPU 불요.

### R1. 감독의 도구가 감독의 렌더를 FAIL 시킨다 (치명)

```bash
python scripts/regression_check.py --before look_check/sceneC2/r2_on \
                                   --after  look_check/sceneC2/balust
python scripts/regression_check.py --before look_check/sceneC2/balust \
                                   --after  look_check/sceneC2/leaf3d
```

| 구간 | 판정 |
|---|---|
| `r2_on → balust`(커밋 3개) | 13컷 중 **FAIL 1 · WARN 4** · INFO 3 · PASS 5 |
| `balust → leaf3d`(커밋 1개, 깨끗한 A/B) | 13컷 중 **FAIL 1 · WARN 3** · PASS 9 |

`balust → leaf3d` 의 FAIL 컷 `preset_h0.3_d5` 사유 전문:

> `[GRAZE] [의심] h0.3 은닉 — 지면 구조량 ×1.46 · 최강 단차 위치 +0.50.
> 지면대 구조가 늘었다 → 숨어 있어야 할 낙차가 드러났을 가능성. **육안 확인 필요**`

이 도구의 docstring 은 `h0.3 로봇 시점`을 **판정 1순위**로 명시한다. 낙엽 커밋은
h0.3 시점의 지면 구조량을 1.46배로 올렸고, 도구는 "숨은 낙차가 드러났을 가능성 —
육안 확인 필요" 라고 이름까지 붙여 경고했다. **감독이 육안 확인한 컷은
`preset_h0.3_d2` 였고, 도구가 확인하라고 지목한 `d5` 는 보지 않았다.**
이건 미관 문제가 아니라 **연구 타당성(비가시 낙차의 은닉)** 문제다.

또한 `scene05/planterfix` 는 아예 컷이 1장뿐이라 도구가 12컷 MISSING 으로 FAIL 한다:

```bash
python scripts/regression_check.py --before look_check/scene05/r2_on \
                                   --after  look_check/scene05/planterfix
# → scene05  FAIL 12 (전부 MISSING) · WARN 1
ls look_check/scene05/planterfix/*.png | wc -l    # → 1
ls look_check/scene05/r2_on/*.png      | wc -l    # → 13
```

`bc87292` 는 "scene05(화단 6개)로 렌더 검증 완료" 라고 보고했다. 실제로는
**13컷 중 1컷(7.7%)**, 그것도 `preset_h1.8_d10`(가장 높고 가장 먼 시점) 하나다.
프로젝트가 1순위로 규정한 h0.3 로봇 시점은 0컷이다.

### R2. 공식 통계 도구를 돌리면 T1 게이트가 통과→미달로 뒤집힌다

```bash
python scripts/imgstats.py @r2_on  'look_check/sceneC2/r2_on/pt_*.png' \
                           @balust 'look_check/sceneC2/balust/pt_*.png' \
                           @leaf3d 'look_check/sceneC2/leaf3d/pt_*.png'
```

| 그룹 | slope | grad_k | flat% | sat_mu | chroma_sd | T1 slope 판정 |
|---|---|---|---|---|---|---|
| r2_on | **−2.021** | 16.60 | 4.00 | 0.378 | 0.0247 | **통과** (−2.2~−2.0) |
| balust | **−1.964** | 11.20 | 3.81 | 0.375 | 0.0284 | **미달** |
| leaf3d | **−1.990** | 9.32 | 4.03 | 0.409 | 0.0341 | **미달** |

같은 13컷 페어링 Δ:

```
r2_on → balust   slope +0.0564 (13컷 중 10컷 상승) · grad_k −5.44 (13/13 하락)
                 chroma_sd +0.0037 (13/13 상승)
balust → leaf3d  sat_mu +0.0340 (13/13 상승) · chroma_sd +0.0056 (13/13 상승)
                 grad_k −1.88 (12/13 하락)
```

`13/13` 동일 방향은 PT 노이즈로 설명되지 않는다. 낙엽 커밋의 확정 효과는
**`sat_mu` 0.375 → 0.409 상승**인데, T1 목표는 0.15~0.22 이므로 **이미 초과하던
지표가 더 멀어졌다**. 동시에 `chroma_sd` 는 13/13 개선됐다. 즉 이 커밋은
"개선"과 "악화"를 동시에 냈고, **감독은 어느 쪽도 알지 못한 채 커밋했다**.
(주: `imgstats.py` 주석 자신이 `sat_mu` 의 판별력을 전 지표 최하위로 적어 두고
게이트 유지를 승인 사항으로 남겼다. 게이트의 타당성은 별개 논점이고, 여기서
반증하는 것은 **감독이 자기 게이트에 대한 자기 위치를 측정하지 않았다**는 사실이다.)

### R4. scene10 은 간살을 두 번 만들고, 실린더가 서로 관통한다

`scenes/main/scene10_park_deck_switchback.py:1020-1032` 은 v6 판정 대응으로
이미 자체 세로살을 만든다(`bal_step=0.30`, `bal_r=0.022`, 디딤면→상부 가로대).
`dada81c` 가 `build_railing_line` 안에 전역 간살을 넣으면서 **같은 난간에 두 벌**이 된다.

```bash
python3 - <<'EOF'
P=2*0.009+0.098; run=3.0
new=[]; xb=P*0.5
while xb <= run-P*0.25: new.append(round(xb,4)); xb+=P
nb=max(1,int(round(run/0.30))-1)
old=[round(run*(i+1)/(nb+1),4) for i in range(nb)]
print(len(new),"개(신규) vs",len(old),"개(기존)")
print([(o,n,round(abs(o-n),4)) for o in old for n in new if abs(o-n)<0.022+0.009])
EOF
```

→ `26개(신규) vs 9개(기존)`, 반경합 0.031 m 이내로 **간섭하는 쌍 6개**
(간격 0.002 / 0.010 / 0.018 / 0.022 / 0.026 / 0.030 m). 최소 2 mm 이격은 사실상
동축이며 Z파이팅 후보다. 플라이트 4 × 양측 2 = **레일선 8개 → 간섭 48쌍.**
scene10 은 렌더되지 않았다.

### R5. 유한차분 기울기(d=0.15)가 계단에서 반환하는 값 — 낙엽 90%가 잘못 눕는다 (치명)

`scatter_debris` 의 `ground_fn` 은 sceneC2 `surface_z` 이고, `surface_z` 는
계단 회랑에서 **계단식**(`terrain_z`: `i = int(x/TREAD)+1; return -RISER*i`)이다.
`d = 0.15 m` 양측차분 창(0.30 m)이 `tread = 0.34 m` 보다 크므로,
**디딤면 위 x 의 88%에서 창이 계단코를 물고** `gx = ±0.16/0.30 = ±0.533` 을 반환한다.
실제 디딤면 국소 경사는 **0** 이다.

`scatter_debris` 의 RNG 소비 순서를 그대로 복제해 845개 전수를 계산했다
(스크립트: `…/scratchpad/rt/leaf_repro.py`, numpy 만 필요):

```
영역 10.46×4.40 = 46.02 m² · mean_cov=0.0435 → n=845          ← 커밋의 "845개" 정확히 재현
배치 845개 · 계단 회랑 위 238개
  [전체]     |기울기| 중앙 11.3° 평균 17.4° 최대 53.2° | >15° 46.3% >25° 29.7%
  [계단 회랑] |기울기| 중앙 27.9° 평균 27.3° 최대 53.2° | >15° 90.8% >25° 60.1% >35° 16.4%
  계단 디딤면(실제 경사 0)인데 |gx|>0.2 로 잡힌 개체: 213개 = 계단 개체의 89.5%
  관측된 gx 값: −0.533(계단코) … −1.222(계단코 + 낙엽 마운드판 경계 중첩)
  등가반경 14.1 cm 기준 가장자리 부유/매몰: 계단 회랑 중앙 6.6 cm · 최대 11.3 cm
                                            (라이저가 16 cm 다)
```

즉 **계단 위 낙엽 238장 중 213장이 수평 디딤면 위에서 평균 28° 로 기울어**,

기울기를 0으로 폴백해야 한다.

감독이 육안 확인한 컷은 `preset_h0.3_d2` 이고, 이 컷의 화면은 **x<0 평탄

### R9. 간살은 난간 높이의 **43%** 만 채운다 — 인용한 법정 요건을 충족하지 않는다

```python
# scene_common.py:1358-1361
ztop = top0 - drop*t - rail_r          # 상단 레일 밑면
zbot = top0 - drop*t - rail_mid_drop   # 중간 레일 중심
h    = ztop - zbot                     # = rail_mid_drop - rail_r
```

간살은 **중간 레일 ~ 상단 레일 사이에만** 선다. 지면 ~ 중간 레일 구간은 그대로 빈다.

| 씬 | rail_h | rail_mid_drop | 간살 높이 | **중간 레일 아래 개방** | 그 구간 실제 안목 |
|---|---|---|---|---|---|
| sceneC2 | 0.90 | 0.42 | 0.392 (43.6%) | **0.48 m** | 포스트 간격 1.20 m |
| scene02·16·20·21 | 0.90 | 0.45 | 0.420 (46.7%) | **0.45 m** | 1.2~2.0 m |
| sceneN4 | 0.95 | 0.42 | 0.392 (41.3%) | **0.53 m** | 2.75 m |
| scene10 | 1.05 | 0.45 | 0.420 (40.0%) | **0.60 m** | 1.05 m |

커밋 메시지: *"세로 간살 **안목 100mm 이하가 법정 요건**이라 예외 없이 촘촘하다"*.
구현된 기하는 **바닥에서 0.45~0.60 m 구간의 안목이 1.05~2.75 m** — 인용한 한도의
**11~28배**다. 그리고 그 하부 개구야말로 100mm 규정이 존재하는 이유(추락·끼임)다.
감독의 비교 시트 `scratchpad/balust.png` 하단 이미지에서 이 빈 구간은 **육안으로
보인다**. 감독은 그 이미지를 보고 "확인" 했다.

곁들여, 같은 블록의 방어 코드는 죽어 있다:

```python
zbot = max(zbot, gz)   # "계단코 아래로 뚫지 않게"
```

이 분기는 `rail_mid_drop > rail_h − (지면이 레일선 위로 솟는 높이)` 일 때만 발동한다.
계단 디딤면은 단코선보다 최대 1 라이저 낮으므로 조건은 `rail_mid_drop > rail_h − riser`
이고, 실호출부 14개에서 좌변 0.42~0.46, 우변 0.72~0.89 — **한 번도 발동하지 않는다.**
간살이 애초에 지면까지 내려오지 않으니 계단코를 뚫을 일도 없다. 주석이 약속한 보호는
장식이고, 실제 결함(하부 개방)은 정반대 방향이다.

## §4 반증 실패 항목 (공격했으나 감독이 옳았던 것)

정직하게 적는다.

1. **`add_vegetation` 의 `/Asset` 이동이 경로 문자열 조회를 깨뜨린다** — **반증 실패.**
   `grep -rn "GetPrimAtPath\|GetAtPath" --include=*.py .` 전수 확인 결과, 식생·화단
   프림을 경로 문자열로 찾는 코드는 `SetInstanceable` 3곳 외에 **존재하지 않는다**
   (scene09 `Pavilion/Roof`, scene07 셰이더는 무관). 경로 변경으로 깨지는 코드 없음.
2. **자식에 참조를 붙이면 나무의 트랜스폼·재질 바인딩이 어긋난다** — **반증 실패.**
   부모 op 순서(T→Rz→[Rx→Ry]→S)는 그대로고, Trees 계열은 자체 루트 op 이 없다는
   전제 하에 최종 합성 결과가 동일하다. 재질은 참조된 프로토타입 내부에 있고
   외부에서 override 를 authoring 하는 코드가 없어 영향 없다. **다만** "Debris 는
   루트 op 이 있고 Trees 는 없다" 는 전제 자체는 이 환경에서 검증 불가였다
   (USDC 크레이트, `pxr` 부재, `strings` 는 토큰 압축 때문에 무효). 감독의 크래시
   로그가 유일한 근거로 남아 있다.
3. **간살 프림 폭증으로 예산이 무너진다** — **반증 실패.** 전 17씬 실인자로 계산한
   간살 총계는 **3,405 프림**(최다 sceneN4 758, sceneD3 327)이고, 암시적
   `UsdGeom.Cylinder` 를 Hydra 기본 테셀레이션(~36 삼각형/개)로 잡으면 **~123k
   삼각형**이다. 관목 1개(Forsythia 404k)보다 적다. **간살은 예산 문제가 아니다.**
   예산 문제는 낙엽 쪽이다(R7: 단일 씬 5.23M, 인스턴싱 무효).
4. **낙엽 개수 산정식이 틀렸다** — **반증 실패.** `n = A·(−ln(1−cover))/개당면적`
   은 겹침을 고려한 올바른 역산이고, 재계산 결과 `n=845`, 달성 피복 0.550 으로
   커밋 메시지와 소수점까지 일치한다. `mean_cov=0.0435`, 영역 46.02 m² 도 일치.
   실측표도 5행 중 4행이 문서와 정확히 일치한다(R8 이 유일한 예외).
5. **`rail_h` 기본값 변경이 씬을 바꾼다** — **반증 실패.** 전 호출부가 `rail_h` 를
   명시 전달한다. 이 부분에 한해 커밋 메시지가 옳다. (`spacing` 은 R3 대로 거짓.)
6. **`ok:false` 인 컷이 손상된 이미지다** — **반증 실패.** `ok` 는 캡처 파일 크기
   안정화 확인 플래그일 뿐이고(`scene_common.py:2520-2530`), 해당 이미지들도
   `imgstats`·`regression_check` 에서 정상 판독된다. 다만 `balust` 라운드는 13컷 중
   4컷이 `ok:false` 로 `r2_on`(2컷)보다 많고, 이 정보는 어디에도 보고되지 않았다.
7. **감독이 절차를 지키지 않았다(전반)** — **부분 반증 실패.** 감사 도중 들어온
   `fb71420`(00:27, 관목) · `d8fd7c2`(00:36, 파사드)는 **scene05 를 13컷 전부**
   렌더했다(`look_check/scene05/shrub`, `look_check/scene05/facade`). 컷 커버리지는
   개선되는 추세다. 다만 그 두 커밋에도 `imgstats`·`regression_check` 산출물은
   0건이고, `d8fd7c2` 가 추가한 `facade_kit.py`·`infra_kit.py`·`stair_kit.py`
   **3,063줄은 `grep -rln "facade_kit\|infra_kit\|stair_kit" scenes/` 결과 0건** —
