## 1. K1 — the tactile registry move (`1a6be6b`)

### 1.1 What was wrong

`w3_s16_v1.md` §2.5 blocker 1, restated by the §7 supervisor adjudication: scene16's statutory
stair-head band was built **scene-side** (`build_tactile_head`, `infra_kit.build_tactile_pair`)
because `ground_kit.py` belonged to another workflow that window. That left three things broken
at once:

1. **B11 asymmetry.** The registry is the authority on where tactile paving may exist, and the
   scene emitted a band the registry did not know about. Registering it without moving the build
   would have inverted the same fault — a registry describing something the kit does not emit.
2. **The ground-kit gates never saw the band.** B6 (GT-E1′), B7 (GT-E2 / the E-band transverse
   slot) and B9 (albedo cap) evaluate `plan_ground` elements. A scene-side prim is invisible to
   all three; `w3_s16_v1.md` had to run them by hand in a **dry** `plan_ground` to get numbers.
3. **`EXPECTED_FP` had no scene16 rows**, so the two GT-E2-x false positives the band
   manufactures had to be written out longhand in the report instead of being derived.

### 1.4 Render A/B — adjudicating the LSB noise

Both arms rendered the **full 13-cut `grid_views` set** — not a 5-cut subset — so the
order-prefix rule (PT/DLSS accumulation carries frame history) is satisfied against the 13-cut
baseline of record. GPU-exclusive under `flock -w 7200 /tmp/negobs_gpu.lock`, arm identical to

The frames are **not** byte-identical. Before attributing that to the edit, the noise floor was

|---|---|---|---|---|

| B vs B₂ | **same tree**, run-to-run | 36 | 0.364 | 0.44 % |

**The cross-tree difference is smaller than, or equal to, the same-tree control.** A₂ vs B₂

the same amount the edit does, so no part of the delta is attributable to the move. The larger
`A vs *` figures are a property of the **first** render of a session (shader/accumulation
warm-up), not of either tree — which is why the control was run at all.

|---|---|

## 2. T4 — the `assets/urban` MDL chain

### 2.1 The defect, reproduced

A minimal test stage (4 urban rock scans — `rock_03_broken` ×2, `rock_02`, `rock_01` — on a
neutral grey ground under the project noon sky, all placed through `add_urban_asset` with
`instanceable=True`, `IsInstance()` true 4/4) reproduces `w3_s07_rebuild_v1.md` §5.1 and
`w3_s10_rebuild_v1.md` §5.2 verbatim `[measured — this session]`:

```
C120 could not find module '.::baking_annotations' in module path      ← SimPBR.mdl(29,7)
C120 could not find module '.::baking_annotations' in module path      ← SimPBR_Model.mdl(29,7)
C121 imported module '::…::SimPBR_Model' contains errors               ← SimPBR.mdl(27,8)
Failed to create MDL shade node for prim '/__Prototype_1/Looks/opaque__stone__rock_03_broken/…'
Failed to create MDL shade node for prim '/__Prototype_2/…'  '/__Prototype_3/…'
```

8 × `C120`, 3 × failed shade node (one per prototype), and the frame comes back with
**11.78 %** (d2) / **5.45 %** (d3) flat-red pixels, max R/G **107**.

The missing module is real: the procured package holds **9** `SimPBR*.mdl` files and
`baking_annotations.mdl` is not one of them, yet four of the nine open with
`using .::baking_annotations import *` (SimPBR · SimPBR_Model · SimPBR_Buildings ·
SimPBR_RoadPaint) and a fifth (`SimPBR_Road`) needs `.::OmniUe4Function` / `.::OmniUe4Base`,
also absent.

### 2.2 Why the fix cannot be a search path — measured, not asserted

`.::x` is a **relative** MDL module path: the resolver looks only in the package directory of
the importing module. The probe was re-run with **both** `MDL_USER_PATH` and `MDL_SYSTEM_PATH`
pointed at the Kit core `Base` directory — which *does* contain `baking_annotations.mdl` —
and all **8 `C120` errors remained** `[measured]`. A search path repairs absolute imports; it
cannot repair this one. The module has to exist next to `SimPBR.mdl`.

### 2.3 Why the fix lives in `urban_kit` and not in the asset tree

`assets/urban/` is **gitignored** (`.gitignore:52`, NVIDIA redistribution forbidden — `git
ls-files assets/urban` returns 0). A file copied there by hand repairs one machine and nothing
else: the next clone runs `assets/download_urban.py` and gets the same broken package back.

So the repair is **`urban_kit.ensure_mdl_package()`** (new section `[1b]`), called automatically
by `add_urban_asset` before the first reference composes, cached after the first call:

1. reads every `.mdl` in `assets/urban/nv_core/materials/`, strips comments, and extracts its
   relative sibling imports (`import .::X::*` and `using .::X import *` forms);
2. for each missing sibling, finds `<name>.mdl` in the **local Kit core MDL tree**, whose root is
   derived from the `OMNIPBR_PATH` this module already depends on (override:
   `NEGOBS_MDL_CORE`), and copies it in **atomically** (temp + `os.replace`, because round
   runners drive 33 scenes through one asset tree);
3. **recurses** — a copied module may import siblings of its own (`OmniUe4Function` does);
4. never raises. A read-only asset tree or an absent Kit install produces one loud
   `_warn_once` naming the unresolved modules and the two ways to fix it, and the scene still
   builds. `..::` (parent-package) imports are reported as unsatisfiable rather than silently
   ignored.

This is the "one place the quirks are implemented once" contract the module was created under,
and it satisfies the constraint that there be **no by-hand per-scene rebinds**: no scene, and no
other kit, has to know the defect exists.

It also became a **gate**: `self_check()` now runs the repair as step 0 and fails if the package
cannot be completed. Every row it loads would otherwise measure perfectly and render red — which
is precisely how the defect reached a judged scene07 frame in the first place.

**Root cause, recorded not patched.** `assets/download_urban.py`'s `CORE_MDL` enumerates the nine
`SimPBR*.mdl` siblings by hand — its own comment says internal MDL `import`s are invisible to
`--resolve` — and the enumeration is short by `baking_annotations`, `OmniUe4Function` and
`OmniUe4Base`. That file, `verify_urban.py` and `urban_manifest_w3.json` belong to the
procurement agent and are read-only for W3 (spec §0), so this is **FU-2** below, not an edit.
