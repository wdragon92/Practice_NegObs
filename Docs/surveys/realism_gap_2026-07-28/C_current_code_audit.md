## 0. 한 페이지 결론

이 파이프라인은 **"치수가 정확한 건축 매스 모델"** 이지 **"사진"** 이 아니다.
장난감처럼 보이는 원인은 셰이딩 튜닝 부족이 아니라 **씬을 구성하는 원자(atom) 자체가
너무 크고 너무 매끈하고 너무 적기 때문**이다. 구체적으로 4가지가 동시에 성립한다.

|---|---|---|

### 1-4. 곡면 표현 — 현(chord) 근사 + 3 % 겹침 **[확인]**

호·나선은 전부 직선 세그먼트 박스의 배열이다.

- `build_arc_steps` (`scene_common.py:423-456`) : 호를 `seg` 개 회전 박스로. 현길이 =
  `2*r_out*sin(dθ/2)*1.03` (`:435`) — **1.03 = 세그 간 3 % 관통 겹침**.
- `build_helix_steps` (`:582-607`) · `build_helix_ramp` (`:610-649`) 동일 규약(`:594`, `:636`).

결과: (a) 곡면 실루엣에 **다각형 각짐**이 남고, (b) 겹친 두 박스의 교차선이 **표면 위 이중
에지**로 보인다. 사내 판정도 같은 것을 지적했다 —
`judge_v8_rt.md` §0 "05 … `rim_view` 예각 쐐기는 **v7과 픽셀 동일**".
렌더 실물 `look_check/scene05/v8_pt/pt_noon_rim_view.png` 좌·우 하단에 **검은 쐐기 틈**이
그대로 남아 있다. `scene06/v8_pt/pt_noon_overview.png` 의 나선 램프 유리 파라펫도 곡선이
아니라 꺾은선으로 읽힌다.

### 1-5. 미세 기복(displacement / subdivision / tessellation) — 0건 **[확인]**

- displacement 맵 입력을 세팅하는 코드 없음. `make_pbr` 은 `mtl:displacement` 출력을
  셰이더에 연결만 하고(`scene_common.py:364-367`) **변위 텍스처는 한 번도 넣지 않는다**.
- `subdivisionScheme` 은 명시된 3곳 모두 `"none"`.
- `PointInstancer` · `instanceable` · LOD · `purpose/proxy` — **전부 0건** (`grep` 확인).

즉 **지면은 수학적 평면**이다. `scene04:598-603` `_flat()` 이 만드는 것은
`(x1-x0) × (y1-y0) × thick(0.5 m)` 짜리 상자 1개. 70 m × 50 m 마당이 프림 1개다.
침하·균열·웅덩이·바퀴자국·포석 단차가 **기하로는 존재할 수 없다**.
현실의 보도는 100 % 미세 기복을 가지며, 그 기복이 만드는 **저각도 그림자 얼룩**이
"바깥에서 찍은 사진"의 1차 신호다. 지금 렌더에서 지면이 거울처럼 매끈한 이유가 이것이다
(`look_check/scene16/v7_pt/pt_noon_beauty_overview.png` 전면 포장 참조).

### 1-6. 폴리곤 예산 — 관리되지 않음 **[확인/추측]**

**[확인]** 코드에는 삼각형 수를 제어하는 어떤 장치도 없다(테셀레이션 설정·LOD·인스턴싱 0건).

### 2-3. UV / 투영 방식 — 월드 스페이스 트라이플래너 고정 **[확인]**

`scene_common.py:344-347`
```python

sh.CreateInput("world_or_object", B).Set(True)
s = 1.0 / float(scale_m)                       # texture_scale = 1/타일크기[m]
sh.CreateInput("texture_scale", F2).Set(Gf.Vec2f(s, s))
```
`uv_mode=True`(메시 st) 는 **18곳 / 15씬**에서 쓰이는데 **예외 없이 전부 한글 사인 패널**이다
(`scene_common.py:1033`, `:1064-1065`; 호출부 `scene01:1064`, `scene02:566`, `scene05:1340`,
`scene07:983`×2, `scene08:824`×2, `scene09:1297`, `scene11:998`, `scene13:661`,
`scene14:847`, `scene16:511`, `scene21:581`, `sceneN3:832`, `sceneN4:630`, `sceneN5:706`).
**지오메트리 표면에 st-UV 를 쓰는 곳은 단 한 곳도 없다** — 전부 월드 투영이다.

이 선택의 3가지 부작용:

- semantic label(`Semantics` 스키마) 부착 0건 → 세그멘테이션 마스크 추출 불가.
- depth / normal / instance-id / bbox 애노테이터 0건.
- 출력은 `capture_viewport_to_file` 로 **RGB PNG 1장**뿐(`scene_common.py:1222-1224`).
  `manifest.json` 에는 파일명·모드·뷰명·성공여부만 기록(`:1252-1272`).
- 씬 파일의 "GT" 언급(`sceneN4:5,17,39,308`, `sceneD4:17`)은 **설계 의도 서술**이지
  구현이 아니다.
- U-Net 학습에 필요한 **낙차량 맵 / 위험영역 마스크**를 만드는 코드는 한 줄도 없다.

즉 "합성 데이터 생성"의 절반(라벨)이 통째로 비어 있다. 다만 **PARAMS 에 모든 치수가
해석적으로 들어 있으므로** 낙차 GT를 해석적으로 산출하는 경로는 열려 있다 **[추측]**.

## 10. 감사자 소견 (우선순위 제언)

1. **먼저 A1 + A6 을 풀어야 한다.** 식생과 물체 수가 지금의 인상을 90 % 만든다.
   Blender → USD reference 경로 하나만 뚫으면 CC0 식생/소품 라이브러리를 통째로
   들여올 수 있고, 그 순간 A5(베벨)·A7(회전)·A9(사람·차)도 함께 해소된다.
2. **A10(GT)은 시각 품질과 무관하지만 논문 성립 조건**이다. 렌더 개선과 병행 착수를 권한다.
   PARAMS 에 치수가 해석적으로 있으므로 Replicator 도입 전에도 **낙차 GT 를 해석적으로
   렌더할 수 있는 임시 경로**가 있다 **[추측]**.
3. **B1(조건 다변화)은 비용 대비 효과가 가장 높다.** 코드 ~160줄 + HDRI 다운로드로
   데이터셋의 조명 다양성이 1 → 6~10 조건이 된다. sim2real 에서 조명 다양성은
   텍스처 품질보다 전이 성능 기여가 크다는 것이 일반적 보고다 **[추측 — 조사 A/B 보고서 확인 요]**.
4. **§6-4 의 위험(슬래브 경계 = 가짜 "도로끝–하늘 접합")은 렌더 품질 이전에
   라벨 오염 문제**다. 브리프의 맥락단서 ②(도로끝–하늘 접합)를 학습시키려는데
   현재 씬에서는 **실제 낙차가 아니라 대지 슬래브가 끝나는 렌더 아티팩트**로도 같은
   패턴이 생긴다. GT 설계 시 반드시 배제 마스크를 두어야 한다 **[추측]**.
5. **§6-5(동적 개체 0)는 맥락단서 ③(스케일 앵커)을 원리적으로 학습 불가능하게 만든다.**
   사람·차량 에셋 도입은 realism 이 아니라 **연구 설계 요구사항**으로 취급해야 한다.
