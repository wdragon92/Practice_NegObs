## 2. 판정 렌더 / 데이터 렌더 이원화 (설계 질문 1)

### 2.1 왜 "그냥 랜덤화하면 안 되는가" — 도구가 구조적으로 막는다

`scripts/regression_check.py` 를 정독한 결과, 변주를 판정 경로에 섞으면 **조용히 틀리는** 지점이 3개다 `[로컬검증]`:

| 지점 | 코드 | 섞였을 때의 결과 |
|---|---|---|
| **뷰 인덱싱이 뷰 이름 단일 키** | `index_round()` (`:323-350`) — `out[s["view"]] = ...`, 폴백 `basename[:-4].split("_",2)[2]` | 조명 조건이 다른 동일 뷰명이 한 폴더에 있으면 **마지막 것만 남는다.** before/after 가 서로 다른 조명끼리 비교되고 **경보 없이** 통과/탈락한다 |
| **GRAZE 판정이 뷰 이름 규약** | `is_graze_view()` (`:354`) — `("h0.3" in v) or ("graz" in v)` | 랜덤 카메라를 `cam0007` 같은 이름으로 쓰면 **판정 1순위 지표가 조용히 꺼진다** |
| **매니페스트 병합이 뷰명 키** | `capture_pipeline():2685` `prev["views"].update(VIEWS)` | 같은 폴더 재실행 시 뷰 좌표가 덮어써져 **과거 라운드의 카메라 좌표 기록이 소실** |

임계값 자체도 이원화를 요구한다. `regression_check.py` 의 FAIL/WARN 은 **"조명·룩이 같은 페어"**

### 2.4 시드 관리 — `hash()` 금지

저장소가 이미 이 버그로 당했다: *"변위 스킨 시드 비결정성 — `hash()` 가 `PYTHONHASHSEED` 로
무작위화 → 매 렌더마다 지형이 달라짐"* (`realism_v1_final.md` §4.2, 중대). 따라서:

```python
import zlib
def var_seed(scene: str, stream: str, idx: int, base: int) -> int:
    """재현 가능한 파생 시드. stream = "cam" | "light" | "expo".
    zlib.crc32 는 프로세스·플랫폼 무관 결정적."""
    key = f"{scene}|{stream}|{idx}|{base}".encode()
    return zlib.crc32(key) & 0x7FFFFFFF
```

- **스트림 분리 필수**: 카메라 표본 수를 바꿔도 조명 추첨이 밀리지 않게 `cam`/`light`/`expo` 를 별도 RNG 로.
- `random.Random(var_seed(...))` 인스턴스를 쓰고 **전역 `random` 을 절대 건드리지 않는다**
  (씬 조립이 전역 `random` 을 쓰는 곳이 있다 — 오염되면 기하가 바뀐다).
- `NEGOBS_SEED` 미설정 시 변주 자체가 비활성이므로 기존 결정성은 자동 보존.

### 3.2 분포 사양

| 파라미터 | 분포 | 절단 | 근거 |
|---|---|---|---|
| **높이 h** | `U(0.25, 1.90)` m | — | ZZ T2-11 / 레드팀 P1-2 그대로. 하한 0.25 = 실물 로봇 카메라대, 상한 1.90 = 보행자 눈높이 상단 |

| **요(yaw)** | `N(0°, 8°)` | `[−20°, +20°]` | 보행/주행 중 헤딩 흔들림 `[추정]`. C팀 B7 은 ±15° 제안 |

**FOV 를 좁게 잡는 이유 (설계 판단)**: FOV 를 크게 흔들면 "겉보기 크기 ↔ 거리" 관계가 깨진다.
그런데 우리 맥락단서 **4계열 중 3번이 스케일 앵커**("수관·차 지붕·사람 상반신이 눈높이 이하")다
(`_context_for_agents.md`). FOV 랜덤화는 지름길을 깨는 축이 아니라 **우리가 쓰려는 단서를 깨는 축**
이므로, **렌즈 불확실성 모델링 수준(±4°)으로 제한**한다. 이것이 "ZZ 권고 FOV 변동"의 우리 해석이다.

**권고 개선 — 피치를 높이와 결합**(선택, `[추정]` 우수):
독립 표집 대신 `d_g ~ LogU(1.5, 12)` 를 뽑고 `p = −atan(h/d_g) + N(0°,2°)` 로 유도하면,
"광축이 쓸모 있는 지면 거리에 떨어진다"는 물리 제약이 자동 충족되고 (h,p) 상관이 씬마다
달라져 탈상관 효과가 오히려 커진다. 독립 표집은 h=1.9·p=−20° 같은 "발밑만 보는 고공 컷"을 만든다.

### 3.4 차폐 검산 자동화 — 2단계

저장소에 이미 있는 자산: **5개 씬(06·08·11·12·19)이 `_solid_at(x,y,z)` + `_obstacle_boxes()`
해석 검산기를 갖고 있다** `[로컬검증]`. 나머지 28씬에는 없다. 28개를 손으로 쓰는 것은
비현실적이므로 **씬 무관 2단 게이트**로 간다.

**1단 — 해석 사전필터 (GPU 불요, 씬 코드 0줄)**

조립 완료 직후 스테이지에서 `UsdGeom.BBoxCache` 로 `/World` 하위 전 프림의 월드 AABB 를 뽑아
균일 그리드에 넣고(23,058 프림 → 수백 ms `[추정]`), 표본마다:

1. **매몰 검사**: `eye` 가 어떤 AABB 내부이거나 표면에서 **0.15 m 이내**면 기각
2. **지면 위 검사**: `eye` 바로 아래로 −Z 레이 → 최초 히트까지 거리가 `[0.05, 3.0] m` 밖이면 기각
   (0.05 미만 = 지면 관통, 3.0 초과 = 허공에 뜬 카메라)
3. **시야 개방 검사**: 프레임을 5×3 으로 나눈 15개 대표 방향 레이 중 **6개 이상이 1.0 m 이상**
   진행해야 통과 (근경 차폐체가 프레임을 삼킨 경우 기각)
4. **식생 예외**: 경로 토큰에 `Veg|Tree|Canopy|Leaf|Shrub|Hedge` 가 있는 프림은 3번에서 제외
   — 임포트 식생의 AABB 는 수관 전체를 감싸 과잉 보수적이다

`_solid_at` 이 있는 5개 씬은 등록만 해 두면 1~3번을 그 함수로 대체(더 정확).

**2단 — 이미지 사후필터 (기존 도구 재사용)**

`regression_check.py` 의 `photometry()` 를 그대로 호출해 컷 단위 자체 판정:

| 조건 | 처리 | 임계 근거 |
|---|---|---|
| `mean < 30` 또는 `dark<25 비율 > 70%` | 데이터셋에서 제외 | `DARK_MEAN_FAIL`/`DARK_PCT_FAIL` — 합격 33씬 412컷 실측에서 유도 `[로컬검증]` |

### 4.3 조건 카탈로그 — 8종 (최소 요구 4종을 상회)

강도 산출식 `[계산]`. 기준(ref)에서 역산한 두 상수와, HDRI 내부의 **직달:천공 비만** 신뢰하고

```
E_phys(h, cloud) = 128000 · sin(h)^1.15 · cloud        [문헌 근사, 전역수평조도 lux]
                   cloud = 1.0(태양 보임) / 0.20(무태양 흐림)   ← 흐림 1~2만 lux vs 맑음 10만
```

### 4.4 태양 고도·방위 산정 규칙 — 서울 천문 정합

**씬에는 북쪽이 없다.** 이것이 설계의 자유도이자 제약이다.

`setup_lighting()` 의 사슬은 `world_az = 33.5 + SUN_AZ_OFFSET` (mod 360) 이다
(scene06·10 이 코드에 명시). 씬 북방위 `N_s` 를 **기준 조건이 남중(방위각 180°)이 되도록** 정의하면:

```
N_s(scene)          = (33.5 + SUN_AZ_OFFSET_ref + 180) mod 360        [정의]
SUN_AZ_OFFSET(c)    = (SUN_AZ_OFFSET_ref + 180 − a_c) mod 360         [유도]
Δaz(c)              = 180 − a_c        (a_c = 조건의 나침반 방위각, 남중=180)
```

## 6. 렌더 예산 공식 (설계 질문 5)

### 6.1 식

```
컷 수      N_cut   = N_scene · N_light · N_cam · (1 + r_reject)
렌더 시간   T_render = N_cut · t_cut
부팅·조립   T_boot   = N_scene · t_boot                       ← 조명은 런타임 전환(§6.3)
하늘 스왑   T_sky    = N_scene · (N_light − 1) · t_swap
총 시간     T_total  = T_render + T_boot + T_sky
```

### 6.2 현재 확보된 상수

| 기호 | 값 | 출처 |
|---|---|---|
| `N_scene` | **33** | 본편 21 + 배치1 12 |
| 씬당 판정 뷰 수 | **13~16 (중앙값 13)**, 33씬 합 **452** | 매니페스트 전수 집계 `[실측]` |
| `t_cut` (PT-fast) | **0.7 s/컷** (프로덕션 실측) | `realism_phase1.md` §3.1 `[실측]` |
| `t_cut` (RT 워밍업 90) | 1.12 s/컷 | D팀 `[실측]` |
| `t_cut` (RT 워밍업 32) | 0.29~0.55 (랩) / 프로덕션 **미측정** | `[추정 0.6]` |
| `t_boot` | 부팅+조립 약 **11~12 s** (룩 레이어 OFF) | phase1 §3.1 환산 `[실측]` |
| `t_boot` (LOOK_V1=1) | **미분리 측정** — 33씬 라운드가 11분→약 30분 | `realism_v1_final.md` §1.3 → `t_boot ≈ 40 s` `[추정]` |
| `t_swap` (HDRI 텍스처 교체 + 정착) | **미측정** | **SP-4** |
| `r_reject` (카메라 표본 기각률) | **미측정** | **SP-3**, 초기 `[추정] 0.08~0.15` |

**렌더 모드 판단 정정**: 레드팀 P1-4 는 "대량 생성은 RT(1.12) vs PT(13.99)" 를 근거로 RT 를
권고했으나, 그 뒤 `realism_phase1.md` 가 **PT-fast 0.7 s/컷**을 실측했다. **PT-fast 가 RT 보다 빠르다.**
→ **데이터 렌더도 PT-fast 단일화.** RT↔PT 룩 불일치 사고(v6~v8 내내 반복)를 원천 제거한다.

### 6.3 조명 조건은 **런타임 루프**여야 한다 — 구조 결정

조명을 프로세스 인자로 두면 `T_boot` 가 `N_scene · N_light` 로 곱해진다.
`N_light=8` 이면 부팅만 33×8×40 s = **2.9시간** — 렌더 시간보다 크다.

→ **`capture_pipeline` 안에서 조명 조건을 바깥 루프로 돈다.**
`setup_lighting()` 이 이미 반환하는 `apply_dome_rot` 에 더해, 조건 전환 콜백을 반환하도록 확장:

```python
apply_dome_rot, apply_light_cond = sc.setup_lighting(stage, PARAMS["light"],
                                                     PARAMS["SUN_AZ_OFFSET"])
# apply_light_cond(cond) : DomeLight.textureFile / intensity,
#                          DistantLight.intensity / angle / rotateX(90−elev),
#                          hdri_sun_rotz_offset, 전역 노출 3키를 한 번에 세팅
```

**루프 순서: 조명(바깥) → 카메라(안쪽).** 하늘 텍스처 스왑을 `N_light−1` 회로 최소화한다.

### 6.4 대입 예시 (표 그대로 계산기로 쓸 것)

`t_cut = 0.7`, `t_boot = 40`, `t_swap = 10 [추정]`, `r_reject = 0.12 [추정]`:

| 시나리오 | N_light | N_cam | N_cut | T_render | T_boot+T_sky | **T_total** | 비고 |
|---|---|---|---|---|---|---|---|
| **judge 1라운드 (현행 유지)** | 1 | 13.7(프리셋) | 452 | 5.3분 | 22.0분 | **약 27분** | 오늘과 동일. 변주 0 |

| data 최소 (4조건 × 20표본) | 4 | 20 | **2,957** | 34.5분 | 38.5분 | **약 1.2시간** | |
| **data 권고 (8조건 × 40표본)** | 8 | 40 | **11,827** | 2.30시간 | 1.01시간 | **약 3.3시간** | |
| data 2만장 목표 | 8 | 68 | **20,106** | 3.91시간 | 1.01시간 | **약 4.9시간** | ZZ 의 "2만 장" 기준 |

1. `T_render` 는 `t_cut` 에 선형이다. SP-5/SP-6(감독 진행 중)의 처리량 실측이 나오면
   위 표의 `0.7` 만 갈아끼우면 전 행이 갱신된다.
2. **인스턴스 증식(§8.3)과 조명 조건 수는 부팅·스왑 오버헤드에서 서로 곱해진다.** 마지막 행에서
   오버헤드가 총량의 56%가 되는 것이 그 결과다. → 인스턴스를 늘릴 때는 **조건 수를 줄이거나**,

## 8. 단서-라벨 탈상관 관점 (설계 질문 7)

### 8.1 정량 논거 — 왜 이 두 축이 최상급인가

- **Early Cue Precision** (arXiv:2606.30344): 단서-라벨 상관 `p=0.10 → conflict accuracy 0.569`,
  `p=1.0 → 0.114`. 텍스처 선택률 **0.049 → 0.855**. 저자 결론 *"단서 탈상관이 아키텍처 선택이나
  입력 열화보다 중요하다"* `[문헌, B팀 확인]`
- 우리 **S1 의 현재 p 는 사실상 1.0** 이다: 지평선이 297장 전부에서 픽셀 행 **247** 이고
  (§1.1 `[계산]`), 씬당 카메라 후보가 9개뿐이라 (씬, 프리셋) → 이미지 y 배치가 **결정론적 사전표**다.
- **S8 도 p=1.0**: 태양 방위·고도가 씬별 상수라 **그림자 방위가 씬 ID 를 그대로 인코딩**한다.
  32/33 씬이 같은 HDRI·같은 고도이므로 하늘 화소는 **씬 간 구분이 없고**, 그림자 방향만 다르다.

**가장 강한 논거는 그림자 밴드다** `[조사, cue_arrangement §2.4~2.5]`:

- 맑은 날 주간 이미지의 **80% 이상**에 선명한 그림자 경계, 그중 보도 횡단 밴드가 1/3~1/2 →
  전체 주간 이미지 기준 **강한 밴드 출현율 0.35~0.5** `[추정]`
- 목표 조건부 확률표가 **`P(낙차 | 그림자 밴드) = base rate (독립 강제)`** 를 명시
- 그런데 우리 데이터는 태양 방위가 씬 상수이므로 **그림자 밴드의 위치·방향이 씬(=라벨)과 완전 상관**이다
- → **조명 방위 변주는 "미관"이 아니라 최대 false-positive 소스의 라벨 상관을 끊는 조치다.**
  게다가 §4.5 스윕이 씬별로 여러 방위를 실제로 만들어 주므로, `negative 씬 20% + positive 씬 동일 비율`
  이라는 조사 권고("그림자 밴드는 positive 씬에도 동일 비율로 — 안 그러면 **그림자=안전** 역지름길")를
  **추가 씬 제작 없이** 충족할 수 있다.

### 8.2 경계 — 변주가 판정 비교성을 해치지 않게 하는 선

| 경계 | 규칙 |
|---|---|
| **B1. 판정 채널 불변** | `judge` 산출물은 조명 `ref` + 프리셋 카메라. **파일명 규약(`{mode}_noon_{view}.png`)과 뷰 이름(`preset_h0.3_d2` 등)을 절대 바꾸지 않는다.** `is_graze_view()` 가 `"h0.3"` 문자열에 의존한다 |
| **B2. 트리 분리** | data 산출물은 `dataset/` 아래. `regression_check --scenes 'look_check/scene*'` 가 절대 만나지 않게 |
| **B3. 기준선 재작성 금지** | 조명·카메라 변주는 `flat%`·`slope`·`grad_k`·판별기 정확도의 **기준선을 무효화하지 않는다** — 왜냐하면 그 지표들은 전부 `judge` 산출물로만 측정하기로 못박기 때문 |
| **B4. 변주 축과 판정 축의 교차 금지** | 예: "조명 변주로 flat% 가 좋아졌다"는 **주장 금지.** flat% 는 `ref` 조명에서만 잰다. 하늘 교체의 flat% 이득(sky_procurement §5.2)을 얻고 싶으면 그것은 **`ref` 조명 자체를 바꾸는 별개 결정**이며 전 기준선 재측정을 수반한다 |
| **B5. 데이터 분할에 변주 축을 흘리지 말 것** | train/val/test 를 조명 조건이나 카메라 높이로 가르면 **분할 자체가 지름길**이 된다. 분할은 **씬 단위**로만 |
| **B6. 변주를 라벨과 상관시키지 말 것** | 조건 배정은 씬·라벨과 **독립 균등**. 예컨대 "어두운 씬엔 밝은 조명" 같은 보정을 넣는 순간 `P(조명 \| 낙차) ≠ base rate` 가 되어 새 지름길을 만든다. 노출 보정은 **조건에만** 의존하고 씬에 의존하지 않는다(§4.3) |

### 8.3 결정적 한계 — 이것만으로는 안 된다 (D9)

현재 판정 세트는 **33씬 × 13~16뷰 = 452컷**이고, **낙차 라벨은 씬마다 상수**다.
따라서 이미지 → 씬 식별 → 라벨이라는 경로가 열려 있고, **카메라·조명 변주는 이 경로를 못 막는다**
(오히려 같은 씬의 변주 컷이 늘어 씬 식별이 더 쉬워질 수도 있다 `[추정]`).

1. **`NEGOBS_PARAMS_OVERRIDE` 기반 씬 인스턴스 증식** — 낙차 깊이·계단 단수·폭·재질을 씬 내에서 지터

**우선순위 판단**: 1·2 는 카메라 랜덤화와 **같은 층위(표본 생성)** 이고 비용이 낮으므로
